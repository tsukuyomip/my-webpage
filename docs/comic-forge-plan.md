# 🗯️ Comic Forge（コマ組み）— 開発プラン

## コンテキスト（なにを作るか）

手持ちのスクショを並べて、**コマ割り → 画像配置 → 吹き出し → 文字**の順に組み上げ、
1枚のコミック風画像として書き出す Web アプリ。
添付された 4 コマ（縦 4 段・縦書き吹き出し・ギザギザ吹き出し・枠外の効果音）が想定する出力の姿。

既存アプリ（`shot-bank` / `media-vault`）と同じく **完全クライアントサイド**、
GitHub Pages の `/comic-forge/` に置く。画像は端末から出ない。

### 決めてもらったこと（この設計の前提）

| 論点 | 回答 | 設計への効き方 |
|---|---|---|
| 主な操作端末 | **iPhone 中心**（PC でも一応使える） | 指で掴める当たり判定・ボトムシート・微調整パッドが必須。レイアウトは1系統で、PC は「幅が広いだけ」 |
| 画像の入り口 | **①ファイル選択 ②共有シート ③Shot Bank** の優先度 | Phase 2 は①のみ。②③は後段のフェーズに回す |
| フォント | **アプリに同梱（サブセット配信）** | 端末に依存せず、保存した zip を別端末で開いても同じ絵が出る。代わりに配信量の設計が要る |
| 作画要素 | **吹き出しとテキストだけに絞る** | 描き文字・集中線・スタンプは作らない。ただしデータモデルは「ページ上のレイヤ」として拡張可能にしておく |

---

## 決定事項

| 項目 | 採用 | 理由 |
|---|---|---|
| **配置** | サブパス `/comic-forge/` | 既存アプリと同じ流儀。Pages 配信で完全クライアントサイド |
| **スタック** | Vite + React + TypeScript | `shot-bank` と同構成。`zip.ts` / `hash.ts` / `download.ts` / `share.ts` をそのまま持ってこられる |
| **描画** | **Canvas2D ひとつだけ**（DOM は操作ハンドルのみ） | 編集画面と出力で**別のレンダラを持たない**。持てば必ずズレる（後述） |
| **描画の中間表現** | `render(doc, scale) → DrawOp[]` → `paint(ctx, ops)` | Node 上（vitest）でも「何を描くか」を検証できる。将来 SVG 出力を足す穴にもなる |
| **コマ割りの構造** | **四角形を再帰分割する木（ギロチン分割）**。ただし節点は矩形ではなく**四辺形** | 「割の移動」で隣のコマが連動して辺が揃うのは木でしか出せない。四辺形にすると斜めのコマ割りが同じ仕組みで載る |
| **吹き出しの形** | 形状をすべて**閉じた折れ線**に落とし、しっぽを折れ線に差し込む | 楕円・角丸・もくもく・ギザギザ・しっぽを**別々の図形として重ねない**。重ねると継ぎ目に線が出る |
| **文字** | Canvas2D に**1文字ずつ自前で組む**（縦書き・ルビ・縦中横） | ブラウザに縦書きの Canvas API はない。仕様は有限なので自前で持ち、単体テストで固める |
| **改行** | **手で入れた改行が正**（自動折返しは補助） | 「改行位置を決められる」が要求。手動が正なら組版は行ごとの単純な積み上げになる |
| **ルビ記法** | 青空文庫式 `｜漢字《かんじ》` を**素のテキストに埋める** | iPhone では `<textarea>` 以外に日本語を打つ現実的な口がない。IME をそのまま使わせる |
| **保存** | **`.zip`（project.json + images/）＋ IndexedDB へ自動保存** | zip は持ち出しと下位互換のため。自動保存は「スマホのタブは黙って死ぬ」ため |
| **取り消し** | 文書まるごとのスナップショット履歴 | 画像を文書の外（ハッシュ参照）に置けば文書は数十 KB。差分管理を書く価値がない |
| **出力** | 同じ `render()` を倍率だけ変えて実行 | 「編集画面と違う絵が出た」を構造的に起こせなくする |

## 先に潰しておく危ないところ

### 1. 編集画面と出力で絵が変わる

コミック作成ツールで一番よくある壊れ方。DOM/CSS で編集して Canvas で書き出すと、
**行の折り返し・字間・縁取りの太さ**が必ずどこかで食い違う。

→ **レンダラを 1 つにする。** 編集画面も出力も同じ `render(doc, scale)` を通す。
違うのは `scale` と描画先のキャンバスだけ。

このために守る規則がひとつある。**寸法はすべて「ページ座標」で持ち、レイアウト計算に `scale` を混ぜない。**
文字の行送りも、しっぽの長さも、枠線の太さもページ座標。最後の `ctx.setTransform(scale, ...)` だけが倍率を知っている。
（枠線と縁取りだけは、倍率を掛けたあと最小 1px を割らないように下限を持つ）

### 2. iPhone のメモリで落ちる

スクショは 1 枚 3〜4MB の PNG。デコードすると **4000×2000×4byte ≒ 32MB** になる。
8 枚置いたら 256MB。iOS Safari はこれで黙ってタブを落とす。

→ 画像は **2 段構え**で持つ。

- **編集中**: パネルに収まる大きさ（画面解像度 × 2 程度）に縮めた `ImageBitmap` だけを持つ。上限枚数を決めて LRU で捨てる
- **出力時**: 必要な倍率の `ImageBitmap` を**1 枚ずつ**作って描いたら即 `close()`。全部同時に載せない

取り込み時にも既定で長辺 2560 / JPEG q88 へ縮める（`shot-bank` と同じ判断。実測で約 1/10）。
原本のまま保つ設定も置くが、既定にはしない。zip が数十 MB になって共有シートが詰まる。

### 3. Canvas の最大サイズ

iOS Safari には面積の上限がある（機種と OS で違う。古いものは 16,777,216px ≒ 4096×4096 相当）。
「解像度も選べる」という要求とまともにぶつかる。

→ 起動時に**実測する**。小さいほうから二分探索で「作れて、右下の画素が読める」最大面積を測り、
**出力の選択肢をその端末で実際に出せる範囲に丸めて出す**（出せないサイズをメニューに並べない）。
測定結果は `kv` に覚えておき、毎回は測らない。

上限を超える出力が要るようになったら、**横帯に切って描き、PNG を自前で継ぎ足す**逃げ道がある
（`CompressionStream('deflate-raw')` があるので PNG エンコーダは自前で書ける）。これは Phase 6 以降の宿題にする。

### 4. フォントが「読み込む前」に描かれる

Canvas2D は、フォントが未ロードでも黙って代替フォントで描く。**エラーにならない**のが厄介で、
初回描画だけ字形が違う・出力だけ違う、という形で出る。

→ **描く前に必ず `await document.fonts.load(fontSpec, 使う文字列)` を通す。**
出力時は全テキストぶんをまとめてロードし、`document.fonts.ready` を待ってから 1 回だけ描く。

### 5. 保存したデータが消える

`shot-bank` と同じ話。iOS Safari は 7 日でスクリプト保存領域を消す。ホーム画面に追加したアプリは対象外になるが、対象外＝永続ではない。

→ **zip 書き出しを Phase 0 に入れる**。1 コマ置けた時点で持ち出せる状態にしておく。
自動保存（IndexedDB）は日常の落ちに対する保険で、zip は端末をまたぐ保険。役割が違うので両方持つ。

## データモデル

```ts
interface Project {
  schemaVersion: number          // 整数。増えるだけ
  writtenBy: string              // "comic-forge <build>"。古い版が新しい zip を開いたときの案内に使う
  meta: { id, title, createdAt, updatedAt }
  page: Page
  layout: Node                   // コマ割りの木（根）
  panels: Record<PanelId, Panel> // 木の葉から引く
  balloons: Balloon[]            // ページ上の順序付きレイヤ（吹き出し＋テキスト）
  assets: Record<AssetHash, AssetMeta>  // 画素は zip / IndexedDB 側
}

interface Page {
  width: number; height: number  // ページ座標（px 相当）
  background: string
  margin: Inset                  // 用紙の余白
  gutter: { x: number; y: number }   // コマ間の溝（既定値。split ごとに上書き可）
  frame: { width: number; color: string; radius: number } // 枠線の既定値
}
```

### コマ割り — 四辺形を割る木

```ts
type Node = Split | Leaf
interface Split {
  kind: 'split'
  dir: 'row' | 'col'       // row = 横線で上下に割る / col = 縦線で左右に割る
  ratios: number[]         // 合計 1。子の数だけ
  tilt: number[]           // 各分割線の傾き（-0.5〜0.5。0 なら水平/垂直）
  gutter?: number          // この分割だけ溝を変える
  children: Node[]
}
interface Leaf { kind: 'leaf'; panel: PanelId }
```

木の評価は**四辺形 → 四辺形**の再帰にする。

```
quadOf(node, parentQuad):
  Split なら、parentQuad を dir 方向に ratios で割る。
    溝の合計を先に取り除き、残りを ratios で分ける（後述）
    分割線の両端点は tilt ぶん互いに逆向きにずらす → 子は矩形ではなく四辺形になる
    各子の境界側に gutter/2 を食い込ませる
  Leaf なら、その四辺形に panel.inset を適用し、panel.rotate で中心回りに回す
```

**溝は「先に引いてから割る」。**（実装して最初に踏んだ落とし穴なので書いておく）
素直に「全体を取り分で割ってから、境界に gutter/2 を食い込ませる」と、
両端のコマだけ片側しか食い込まれないぶん大きくなる。4 等分したはずが 1 コマ目と
4 コマ目だけ 12px 高い、という形で出た。溝の合計 `(n-1)*gutter` を先に引き、
残りを取り分で分ける（CSS の grid gap と同じ考え方）。
辺の長さは左右で違いうるので、溝の割合は辺ごとに計算する。

矩形ではなく四辺形で持つのがこの設計の要。**斜めのコマ割りが、まっすぐなコマ割りと同じコードで出る**。
四辺形を直線で割った結果はまた四辺形なので、入れ子にしても破綻しない。
クリップは `ctx.clip()` に多角形を渡すだけ、枠線はその多角形をなぞるだけで済む。

```ts
interface Panel {
  id: PanelId
  inset: Inset                   // 「margin 的な個別サイズ調整」。割り当てられた枠から内側へ
  rotate: number                 // コマ自体の角度（度）
  frame?: Partial<Page['frame']> // このコマだけ枠線を変える／消す
  content?: {
    asset: AssetHash
    x: number; y: number         // コマ中心からのずれ（ページ座標）
    scale: number; rotate: number
    flipX?: boolean
  }
}
```

**コマの追加・削除・移動が木の上でどうなるか**（この構造の素直な帰結として、先に書いておく）:

| 操作 | 木への作用 |
|---|---|
| 追加 | 選んだ葉を `Split` に置き換え、元の葉と新しい葉を子にする（「このコマを横に割る」） |
| 削除 | 葉を消し、親の `ratios` から抜く。子が 1 つになった `Split` は親に畳む |
| 入れ替え | 2 つの葉の `PanelId` を交換する（中身ごと入れ替わる） |
| 並べ替え | 同じ `Split` の子の順序を入れ替える |

**ギロチン分割にできないこと**を隠さずに書く: コマを木と無関係な場所へ自由に放り込むことはできない。
必要になったら「木から外した自由コマ（四辺形を直接持つ葉）」を足す穴を空けておく（Phase 5 の任意項目）。
最初からそれを許すと、辺が揃うという最大の利点を捨てることになる。

### 吹き出し

```ts
interface Balloon {
  id: string
  anchor?: PanelId               // 指定するとコマの移動・変形に追従する
  clip: boolean                  // false ならコマ枠をはみ出して描ける
  x, y, w, h, rotate             // ページ座標（anchor があればコマ中心からの相対）
  shape: 'ellipse' | 'round' | 'rect' | 'cloud' | 'burst' | 'none'
  shapeParams: { amplitude?: number; count?: number; radius?: number }
  fill: string; stroke: string; strokeWidth: number
  tails: Tail[]
  text?: TextBlock
}
interface Tail {
  at: number        // 輪郭上の位置（0〜1）。しっぽの向きはここで決まる
  spread: number    // 根元の幅（輪郭の弧長に対する割合）
  len: number       // 伸ばす長さ（ページ座標）
  bend: number      // 曲がり（0 で直線）
  aim?: number      // 角度の微調整（度）
  style: 'solid' | 'spike'   // 通常のしっぽ / ギザギザ用の尖ったしっぽ
}
```

**形もしっぽも、最後は 1 本の閉じた折れ線になる。**（実装済み）

```
outline(shape, w, h) → Point[]      // 楕円もギザギザももくもくも、密にサンプルした閉じた折れ線
  ↓
splice(outline, tail)               // 根元の区間を取り除き、代わりに [根元左 → 先端 → 根元右] を差し込む
  ↓  （しっぽの数だけ繰り返す。位置が重なるものは弾く）
1 本のパスを fill して stroke する
```

楕円としっぽを別々に描いて重ねると、必ず継ぎ目に線が残る（塗りで隠しても縁取りが切れる）。
最初から 1 本の輪郭にしてしまえば、この問題そのものが消える。

**差し込みは「弧長の順に並べ直して吐き出す」。**（実装して踏んだ落とし穴）
頂点を前から走査して「切り欠きの区間に入ったらしっぽを置く」と書くと、
切り欠きが最後の頂点より後ろ（＝輪郭を閉じる手前の辺の中）にあるとき一度も入らず、
しっぽが黙って消える。頂点の少ない四角と角丸で実際に落ちた。
頂点と切り欠きを弧長でまとめて並べてから順に出せば、この場合分けそのものが要らなくなる。
`cloud` は基準楕円に沿った円弧の連なり、`burst`（添付画像の「ツインアホ毛！」の形）は
基準楕円を内外に振った鋸歯 — どちらも `outline()` の実装違いに収まる。

### テキスト

```ts
interface TextBlock {
  source: string                 // 生テキスト。改行は \n、ルビは ｜漢字《かんじ》
  vertical: boolean              // 既定 true（吹き出しは縦書き）
  font: FontId                   // 同梱フォントの id
  size: number; lineHeight: number; letterSpacing: number
  align: 'start' | 'center' | 'end'   // 行方向の揃え
  color: string
  stroke?: { color: string; width: number }   // 白縁取り
  autoShrink: boolean            // 吹き出しに収まらなければ縮める
  tateChuYoko: 'auto' | 'off'    // 半角数字を寝かせるか回すか
}
```

`source` を素のテキストのまま持つのは、**iPhone で編集できる形がそれしかない**から。
リッチな構造を持つと、専用のキャレット処理を書くはめになり、IME と喧嘩する。
`<textarea>` に流し込んで、出てきた文字列を毎回パースする。パーサは純関数なのでテストで固められる。

```
parse(source) → Line[] → Run[]
  Run = { text, ruby?, kind: 'normal' | 'tcy' }
```

## 縦書きの組み方（Canvas2D に自前で組む）

ブラウザに Canvas の縦書き API はない。1 文字ずつ置く。規則は有限。

| 種類 | 対象 | 処理 |
|---|---|---|
| そのまま | 大半の漢字・かな | 字幅の中央に置き、行送りぶん下へ進む |
| 90° 回す | `ー 〜 ─ ： ；` と括弧類 `「」『』（）［］｛｝〈〉《》` | フォントの縦書き字形（`vert`）は Canvas から呼べないので、自分で回す |
| 右上へ寄せる | `、。，．` | 全角の左下に来ている字を、縦書きの位置（右上）へ平行移動 |
| わずかに右上へ | 小書き `ぁぃぅぇぉっゃゅょゎヵヶ` とカタカナの対応字 | 縦組みでの見えを合わせる |
| 縦中横 | 半角数字 1〜2 桁、`!!` `!?` | 1 マスの中に横に詰めて置く。3 桁以上は回す |
| ルビ | `｜親字《ルビ》` | **縦書きでは親字の右**、横書きでは上。親字の長さに合わせて字間を散らす。親字より長ければはみ出しを許す |

行の折り返しは**手動が正**。自動折返しは「1 行の最大文字数」を指定したときだけ働く補助機能とし、
そのときだけ禁則を見る（行頭に来られない `、。」）ゃゅょっー！？`、行末に来られない `「（`）。

**測定は注入する。** レイアウトは `measure(text, font) → width` を受け取る純関数にして、
ブラウザでは `ctx.measureText`、テストでは「全角 1.0 / 半角 0.5」の擬似測定を渡す。
これで縦書き規則もルビの位置も Node 上の vitest で固められる。

## フォント（同梱・サブセット配信）

漫画らしさの大半はここで決まる。**アンチック体**（かなは明朝寄り、漢字はゴシック）が吹き出しの定番。

**仕掛け**: 2 つのフォントを重ねるのではなく、**Canvas のフォントスタックの代替に任せる**。

```js
ctx.font = '40px "GenEi Antique Kana", "Gothic", sans-serif'
```

かなだけを持つアンチックのサブセットを先に置けば、**かなはアンチック、漢字はゴシック**が
文字単位の代替として自動で起きる。かなだけのサブセットは 100KB 前後にしかならないので、
本物のアンチック体を数 MB 抱え込まずに済む。

| 用途 | フォント | ライセンス | 備考 |
|---|---|---|---|
| セリフ（既定） | 源暎アンチック（かなのみ）＋ ゴシック | OFL | 上の重ね方。ライセンス文をリポジトリに同梱する |
| ゴシック | Noto Sans JP 系 | OFL | 漢字担当も兼ねる |
| 明朝 | Noto Serif JP 系 | OFL | ナレーション・モノローグ用 |

配信は **`unicode-range` で分割**する（漢字の常用域を 10 前後のチャンクに割り、使う範囲だけ取りに行く）。
`build` 時に `scripts/subset-fonts.mjs` で生成し、Service Worker でキャッシュする（オフラインでも同じ絵が出る）。
どのチャンクを取るかは「文字が使われたとき」に決まるので、**描画前の `document.fonts.load()` が必須**（前述）。

## 保存（`.zip`）と下位互換

```
comic-forge-20260902-2140.zip
├ project.json          スキーマ版・ページ・木・コマ・吹き出し・文字（画素は入らない）
├ images/<sha1>.jpg     取り込んだ画像。ハッシュで重複排除
├ preview.png           一覧とファイラ用の縮小画像
└ README.txt            どのアプリの何版が書いたか（人が読む用）
```

zip の読み書きは `shot-bank/src/lib/zip.ts` をそのまま持ってくる（依存なし、
書き出しは無圧縮 store、読みは store と deflate の両方に対応済み）。`project.json` だけは
`CompressionStream('deflate-raw')` で縮めてもよいが、まずは素で入れる（人が中を覗ける利点のほうが大きい）。

**「下位互換」を、実際に守れる形にする。**

- `schemaVersion` は整数で単調増加。**新しいフィールドは必ず既定値を持ち、古いデータから計算できること**を条件にする
- 読み込み時に `migrate[v]` を鎖のように適用して最新版まで持ち上げる。書き出しは常に最新版
- **過去の版で書いた zip を `src/lib/__fixtures__/projects/v1.zip` … として置き、
  「読めて、移行できて、描画命令が期待通り」まで自動テストで見る。** これを置かない限り下位互換は口約束にしかならない
- 逆向き（古いアプリが新しい zip を開く）は**直せないので、黙って壊さない**ことだけを保証する。
  `schemaVersion` が知らない値なら「この作品はもっと新しい版で作られています」と出して読み込みを止める

自動保存は IndexedDB（`comic-forge` / `projects` / `assets` / `kv`）。編集のたびに 500ms のデバウンスで書く。
作品一覧を持ち、アプリを開き直したら続きから戻れるようにする。

## 取り消し／やり直し

`Project` は不変オブジェクトとして扱い、あらゆる編集は `apply(doc, command) → doc` を通す。
履歴は**文書まるごとのスナップショット**（画像は外にあるので 1 件数十 KB）。上限 100 手。
ドラッグ中は履歴に積まず、指を離したときに 1 手だけ積む（`begin/commit` を持つ）。

「これまでの操作は順不同であとから調整できる」という要求は、**UI をウィザードにしない**ことで満たす。
モードバー（コマ / 画像 / 吹き出し / 文字）は「いま何を触るか」を選ぶだけで、作業の順序を強制しない。

---

## 出力

- 倍率ではなく**仕上がりの幅**で選ばせる（1200 / 1600 / 2048 / 自由）。高さはページの縦横比から決まる
- 端末で実際に出せる上限（前述の実測）を超える選択肢は**そもそも出さない**
- 形式は PNG（既定）／ JPEG（品質つき）／ WebP
- 書き出しは「フォントを全部ロード → 画像を必要な倍率で 1 枚ずつ載せて描いて捨てる → `toBlob`」
- 渡し方は `navigator.share({ files })` を第一手、駄目なら `<a download>`（`shot-bank/src/lib/share.ts` の流儀）
- `toBlob` が `null` を返す（iOS で大きすぎるとき）場合は、一段小さい幅で描き直して案内する

## 画面（iPhone を主、PC は幅が広いだけ）

```
┌──────────────────────┐
│ ← 作品名        ↩ ↪  ⋯ │  上バー（取り消し／やり直し／メニュー）
├──────────────────────┤
│                      │
│      キャンバス        │  ページ全体を表示。2本指で拡大・移動
│   （選択中に大きめの    │  タップで最前面の要素を選択
│     ハンドルを重ねる）   │
│                      │
├──────────────────────┤
│ [コマ][画像][吹][文字]  │  モードバー（順不同。作業を強制しない）
├──────────────────────┤
│  インスペクタ（ボトム    │  選択中の要素の設定。スライダ＋数値入力
│  シート。引き上げ可）    │  ＋ 十字の微調整パッド（1px 単位）
└──────────────────────┘
```

指で操作するために必要になるもの:

- **当たり判定は見た目より広く**（44pt 以上）。ハンドルは要素の外側に出し、指で隠れないようにする
- **微調整パッド**を必ず置く。スマホのドラッグは粗い。しっぽの先やコマの溝は指では合わない
- **吸着**（コマの辺・中心・他の吹き出し）と、吸着中に出る補助線。長押しで吸着を切る
- **虫めがね**: しっぽの先やコマの角を掴んでいる間、指の近くに拡大表示を出す
- 文字はボトムシートの `<textarea>` で編集し、上のプレビューに即反映（IME をそのまま使う）
- `touch-action: none`、`overscroll-behavior: none`、ダブルタップ拡大の抑止。ブラウザのジェスチャを全部止めて自前で持つ

## 描画の作り（テストできる形）

```
doc ──render(doc, scale)──▶ DrawOp[] ──paint(ctx, ops)──▶ Canvas
                              │
                              └─▶ vitest でそのまま検証（ブラウザ不要）
```

`DrawOp` は `{ type:'clip'|'image'|'path'|'text'|'restore', ... }` の平たい配列。
「コマ 3 の中に画像がこの矩形で入り、枠が 4px で引かれ、吹き出しの輪郭は 1 本の閉パスで、
文字は 12 個のグリフがこの座標に並ぶ」までを Node 上で確かめられる。

テストする対象:

| 対象 | 見るもの |
|---|---|
| 木の評価 | 分割比・溝・傾き・個別 inset を入れたときの四辺形の座標。合計面積とページ内包 |
| 木の編集 | 追加・削除・入替のあと、木が壊れていないこと（子 1 つの Split が残らない等） |
| 吹き出しの輪郭 | 閉じていること・しっぽの数だけ突起があること・自己交差していないこと |
| 縦書き | 上の規則表の 1 行ずつ。回す字・寄せる字・縦中横・ルビの座標 |
| ルビのパース | `｜` の有無、`《》` の入れ子、壊れた記法（閉じ忘れ）を落とさないこと |
| zip 往復 | 書いて読んで同じ文書になること。過去版 fixture の移行 |
| 出力 | 倍率 1 と 2 の `DrawOp` が、座標以外すべて一致すること（＝倍率で組版が変わらないことの証明） |

## フェーズ

要求の順番（1 コマ割り → … → 7 出力）とは少しずらす。
**保存と出力を最初に通す**のは `shot-bank` と同じ理由で、
「作ったものを取り出せない状態」を一日でも作らないため。

| Phase | 中身 | 終わったときにできること | 状態 |
|---|---|---|---|
| **0. 骨組み** | Vite/React/TS、ページ設定、`render/paint`、IndexedDB 自動保存、zip 保存・読込 v1、白紙の書き出し | 空のページを保存して読み戻し、PNG に出せる | ✅ |
| **1. コマ割り** | 四辺形の木、分割・削除・比率ドラッグ、溝、傾き、個別 inset、枠線、プリセット（4 コマ縦 / 2×2 / 1 コマ） | 添付画像と同じ 4 段のコマ枠が組める | ✅ |
| **2. 画像配置** | ファイル選択、縮小取り込み、コマ内の移動・拡大・回転、2 本指操作 | スクショを並べた「絵だけの」ページができる | ✅ |
| **3. 吹き出し** | 輪郭の折れ線化、5 形状、しっぽの差し込み、複数しっぽ | 添付画像の丸・角丸・ギザギザが再現できる | ✅（吸着は未実装） |
| **4. 文字** | 縦書き組版、手動改行、ルビ、同梱フォント、自動縮小、縁取り | セリフが入って「作品」になる | これから |
| **5. 調整** | コマの入替・レイヤ順・複製、虫めがね、吸着 | 順不同で直せる | 一部（取り消し・入替・微調整パッドは Phase 0/1 で入れた） |
| **6. 出力** | 解像度の選択、上限の実測、形式、共有シート、失敗時の縮退 | 端末で出せる最大の絵を取り出せる | ✅（帯に切る逃げ道は未実装） |
| **7. 入り口を増やす** | 共有シートからの受け口（Share Target / PWA）、Shot Bank の IndexedDB 読み取り | 撮ったスクショが数タップでコマに入る | これから |

取り消し・やり直しは横断的なので Phase 0 から入れてある（あとから足すと全操作を書き直すことになる）。

Phase 7 の Shot Bank 連携は、同一オリジン（`tsukuyomip.github.io`）なので
`indexedDB.open('shot-bank')` で**読むだけ**なら届く。ただし他アプリの内部形式に寄りかかることになるので、
**読み取り専用・失敗しても平気（無ければ入り口を出さない）**という作りに閉じ込める。
