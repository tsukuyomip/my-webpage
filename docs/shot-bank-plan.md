# 📸 Shot Bank（スクショバンク）— 開発プラン

## コンテキスト（なにを作るか）

ゲーム（学マス想定）のスクリーンショットを**端末内に貯め込み**、
**セリフ・表情・キャラ**の3軸で瞬時に絞り込んで、
選んだ候補を**そのまま LINE に送る**ための Web アプリ。

「撮ったはいいが二度と発掘できないスクショ」を、
**送りたい瞬間に3秒で取り出せる**状態にするのが目的。

### 入力として想定する画面（実測10枚から）

画面は**3つの UI 要素の組み合わせ**でできていて、それぞれ独立に出たり出なかったりする。
「レイアウトを4種に分類する」のではなく、**要素ごとに検出して、組み合わせで種別を決める**のが正しい。

| UI 要素 | 位置 | 中身 | 出ないことがある |
|---|---|---|---|
| **ヘッダチップ** | 左上（高さの 8〜14%） | 「親愛度 / 第22話」。カードストーリーなら**丸い顔アイコン＋「藤田 ことね / 冠菊 1話」** | UI 非表示・横 |
| **本文パネル＋話者チップ** | 下部 | 明るい角丸パネル。左上に話者名の小さなチップ | **セリフのない間**・UI 非表示・横 |
| **操作バー** | 最下部 | 角丸ピルが4〜5個（`[ ]` / SKIP / ログ / AUTO or ×1.0 / 早送り） | UI 非表示・横 |

観測できた組み合わせ:

| 組み合わせ | 例 | 備考 |
|---|---|---|
| ヘッダ＋パネル＋バー | 画像2,3,4,9,10 | 通常の ADV。いちばん多い |
| **ヘッダ＋バー（パネルなし）** | 画像8 | セリフのない「間」。**話数は読めるがセリフはない**。誤って「UI なし」と判定してはいけない |
| 要素なし | 画像1 | UI を消して撮ったスクショ（操作バー左端の `[ ]` がその切替） |
| 横・字幕 | 画像5,6,7 | パネルなし。中央下に**縁取り白文字の字幕**、その直下に小さく話者名。位置は3枚とも安定（字幕 78〜82%、名前 87% 付近） |

**寸法は端末で変わる**（1206×2622 と 1179×2556 が混在。比が 2.174 と 2.168 で微妙に違う）。
UI はセーフエリア基準で上下端にアンカーされるため、**「高さの何割」で切ると機種でズレる**。
→ 座標は固定値にせず、**探索レンジ＋実画像からの検出**で決める（後述）。

**キャラの写り方も1枚1様ではない。** 実測10枚で以下が全部出てきた。

- **複数人が同時に写るのが普通**（画像1・6・8は複数の3Dモデル、画像4・10は3Dモデル＋2D立ち絵）
- **顔がそもそも無い**。画像6・7の手前のキャラは**完全な後ろ姿**。画像9の手前は**大きくボケた被写界深度外**。
  → 検出できる顔の数は、写っている人数より**必ず少なくなる**
- **大きさも位置もバラバラ**。画像1の奥はガラス越しで小さく枠に切られ、
  画像8は2人とも全身なので**顔が高さの1割以下**。画像4・10の2D立ち絵は前景の左下にいる
- **同じキャラに「3Dモデル」と「バストアップ2D立ち絵」の2形態がある**。質感が別物
- **パネルの不透明度に幅がある**。画像3は後ろが透けるが、画像9はほぼ純白で不透明
- **操作バーの文言は一定でない**（画像2は `×1.0`、他は `AUTO`）→ **文字ではなくピルの並びで検出する**

→ 「上半分の中央を切れば顔がある」という前提は**最初から成り立たない**。顔検出が要る（後述）。

## 決定事項

| 項目 | 採用 | 理由 |
|---|---|---|
| **配置** | サブパス `/shot-bank/` | 既存アプリと同じ流儀。完全クライアントサイドで Pages 配信。 |
| **スタック** | Vite + React + TypeScript | `media-vault` / `mixer` と同構成。既存コードをそのまま持ってこられる。 |
| **保存先** | **IndexedDB**（localStorage は不可） | localStorage は 5MB 前後の上限＋文字列のみ。実測でスクショ1枚 3.0〜3.6MB の PNG。桁が2つ足りない。 |
| **保存形式** | **JPEG 品質88 に再エンコード（既定）／原本のまま（任意）** | 実測10枚で **31.9MB → 3.0MB**（1枚あたり約 300KB、およそ 1/10）。原本 PNG のままだと 500枚で 1.7GB のところ 0.15GB に収まる。WebP はさらに小さいが **LINE 側の受け取り相性が読めない**ので既定にしない。 |
| **文字認識** | tesseract.js（jpn + eng、資材は自前配信） | `media-vault` の構成をそのまま流用。ただし**全画面ではなくテキスト領域だけを切って**渡す（速度・精度とも段違い）。 |
| **キャラ判定（主）** | **話者名の OCR → 名簿への編集距離照合** | 名前は数文字・字形が明瞭・母集団が有限。ほぼ確実に当たる。まずここで確定させる。 |
| **キャラ判定（従）・表情判定** | **CLIP 埋め込み＋kNN（手タグから学習）** | 汎用モデルの決め打ちでは「ドヤ顔」「ドン引き」は当たらない。自分で付けた数枚を教師にすれば自分の感覚に寄る。埋め込みは「似た画像を探す」にも再利用できる。 |
| **LINE 送信** | **Web 共有シート `navigator.share({ files })`** | 静的サイトから LINE に画像を渡す唯一の実用手段。`line.me/R/share` はテキストのみで画像を運べず、Messaging API はサーバとBotが要る。 |
| **永続化** | **PWA（ホーム画面に追加）＋ ZIP バックアップ** | iOS Safari は7日間未使用で IndexedDB を消す。ホーム画面 Web アプリは対象外になる。バンクとして成立させる生命線。 |
| **検索インデックス** | **貼らない（全件走査）** | 数百枚ならメタ情報は全部メモリに載る。数百件 × 数十文字の `indexOf` は 1ms 未満。転置インデックスは1万枚を超えてから。 |

## 最大のリスクを先に潰す — iOS のデータ消失

メイン端末が iPhone / Safari なので、**これが設計上いちばん危ない**。

- Safari は「スクリプトから書ける保存領域」（IndexedDB / localStorage / Cache API / SW 登録）を、
  **Safari を使った日が7日、そのサイトに触れないまま過ぎたら**消す。
  **カレンダーの7日ではなく Safari の使用日数**で数える。
- **ホーム画面に追加した Web アプリはこの対象外**になる。Safari の外なので自分専用のカウンタを持ち、
  アプリを使うたびにリセットされる（使わなければ進まない）。この経路では実質消えなくなる。
- **ただし「対象外」＝「永続」ではない。** アイコンを消せばデータも消えるし、
  端末の空き容量が足りなければ回収されうるし、OS の更新で飛んだ事例の報告もある。
  `navigator.storage.persist()` が許可される保証もない。
  → **ホーム画面追加で日常の消失を防ぎ、ZIP バックアップで残りを引き受ける**という二本立てにする。
  この2つは冗長ではなく役割が違う。
- したがって：
  1. 初回起動時に **「ホーム画面に追加」を強く案内する**（読み飛ばせるが、未追加なら常時バナー）
  2. `navigator.storage.persist()` を要求し、`estimate()` の使用量を設定画面に常時表示
  3. **ZIP バックアップを Phase 0 に入れる**（データが入った瞬間から退避手段がある状態にする）
  4. 最終バックアップからの経過日数を数え、**2週間を超えたら警告**を出す

「あとで作る」にしない。1枚目を保存できるようになった時点で、書き出せるようにする。

## アーキテクチャの肝

### 1. レイアウト判定と領域切り出し — 固定座標ではなく「検出」

**実測で分かったこと（Phase 1 で確認）**: パネルは本文の行数で伸び縮みしない。
1 行の画面も 2 行の画面も、上端は画像高の 74.3〜75.7%、下端は 84.2〜86.5% に収まった。
とはいえ機種で寸法が変わる以上、固定の座標では切れない。探す窓を決めて、その中で実測する。

```
パネルの「左右の余白」だけを見る
  （x 6〜10% と x 90〜94%。本文はここに来ないので、常に無地）
  ↓
各行について、その 2 本の帯が [明るい] かつ [横方向に平坦] か
  ↓
条件が続く帯のうち、上端が 68〜80% に入り、高さが 5% 以上のもの = 本文パネル
  ↓
話者名チップ = パネル上端のすぐ上。縦の位置だけ色の続きで実測し、大きさは比率で置く
ヘッダチップ = 上部 8〜15% の帯を OCR して、話数の書式が読めたら「ある」とみなす
```

**「明るさ」では絵と区別できなかった。** 最初は「明るい画素の割合」で試し、次に
「全幅にわたって明るいか」で試したが、どちらも白い服を拾った（画像 08 の白いパーカーが
全幅で明るく出る）。パネルと絵を分けるのは明るさではなく **左右の余白まで平坦かどうか**。
本文はパネルの内側にしか来ないので、余白の帯は無地のままで、絵ならそこがざらつく。
この 1 点で 10 枚すべてが正しく分かれた。

- **パネルは半透明**で、後ろのキャラがうっすら透ける（画像3で顕著）。それでも
  左右の余白は平坦なので、この見方なら透けても取れる。
- **話者名チップは大きさの決まった UI 部品だった。** 実測で幅は 466/1206 と 456/1179
  ＝どちらも画像幅の 38.6%、高さは 2.33% と 2.35% で、名前の長さ（「ことね」と「2941」）にも
  端末にも依らなかった。動くのは縦の位置だけなので、そこだけ測って大きさは比率で置く。
  色で右端を追う方法も試したが、縁の影と縦のグラデーションで手前で止まった。
- **チップの箱は実測値より内側に取る。** 1px でも外へはみ出すとチップの外の暗い部分が入り、
  二値化の基準がそちらに寄って白字が地に溶ける（実測で 1 枚が真っ白になった）。
- **要素は独立に見る。** 「パネルが無いから UI なし」と決めつけない
  ── 画像8は**ヘッダと操作バーはあるがパネルだけ無い**。
  ここを一本道の分岐にすると、話数が読めるはずのスクショを取りこぼす。
- **ヘッダの有無は画素ではなく OCR で決めた。** 半透明のチップを任意の背景の上から
  画素だけで見分けるのは当てにならない。一方「話数の書式が読めたか」なら確かめられるし、
  それはそのまま欲しい情報でもある。読めなければヘッダ無しとみなす。
- **操作バーの検出は作らなかった。** 種別を決めるのに要らなかったためで
  （ヘッダとパネルの有無で足りる）、何も依存していない検出を増やすと壊れ方が増えるだけ。

  | ヘッダ | パネル | バー | 判定 |
  |---|---|---|---|
  | ○ | ○ | ○ | 縦・ADV（通常） |
  | ○ | ✕ | ○ | 縦・ADV（セリフなしの間）→ **ヘッダだけ読む** |
  | ✕ | ✕ | ✕ | 縦・プレーン（UI 非表示） |
  | 横長 | — | — | 横・ストーリー（字幕を読む） |

- **操作バーは文言で探さない。** `×1.0` と `AUTO` が入れ替わる。
  最下部に**半透明の角丸ピルが横一列に4〜5個**並ぶ形として検出する。
- **横・ストーリー**はパネルがないので別扱い。字幕は「縁取り付きの白文字」なので、
  高輝度でしきい値を切り、縁の暗色でつながりを補強して行を拾う。
  下段に一回り小さい話者名がある。
  → **ここだけは精度が落ちる**ことを前提に、手修正動線を最初から用意する。

`layout.ts` / `crop.ts` は **DOM 非依存の純関数**にする。
`gkms-sprtcrd` が `screenshot.test.ts` + pngjs で実スクショの回帰テストを回している流儀に合わせ、
**上の10枚をそのままフィクスチャにして** vitest で固定する。
特に「パネルなし ADV（画像8）」「不透明パネル（画像9）」「透けるパネル（画像3）」は
検出しきい値の境界そのものなので、必ず回帰に入れる。**ここが壊れると全部壊れる。**

### 2. 認識パイプライン（1枚あたり）

```
デコード → 向き・寸法
   ↓
保存形式に再エンコード（既定 JPEG q88）＋ サムネ生成（幅400 WebP）
   ↓
dHash 算出 → 既存と近ければ「重複では？」と取り込み時に確認
   ↓
レイアウト判定 → 領域切り出し（本文 / 話者名 / ヘッダ）
   ↓
前処理（2倍拡大・グレースケール・二値化）→ tesseract.js (jpn+eng)
   ↓
話者名を名簿に照合（編集距離）→ characterId 確定
ヘッダを解析 →「親愛度 第24話」「冠菊 1話」→ ストーリー種別・話数
   ↓
顔クロップ → CLIP 埋め込み（512次元）
   ↓
kNN でキャラ候補・表情候補を信頼度つきで提案
   ↓
保存 →（自信が低ければ）「要確認」キューへ
```

- **各段は独立して再実行できる**（再OCR だけ、再埋め込みだけ）。
- **手で直した項目は自動処理で上書きしない**（`textEdited` / `charactersEdited` などのフラグで守る）。
- 取り込みは**キュー＋並列度制限**。数十枚まとめて放り込んでも UI は止めない。
  進捗は残件数で見せ、**中断しても再開できる**ようキューを永続化する。

### 3. 「使うほど賢くなる」ループ

自動判定は**確定させず、提案として出す**。

```
取り込み → 自動で候補を出す（薄いチップで「ことね?」「ドヤ顔?」）
   ↓
タップで確定 / 長押しで却下
   ↓
確定したものが、そのまま次の学習データ（ラベル付き埋め込み）になる
   ↓
kNN の母集団が増える → 提案が当たるようになる
```

**UI から、名前つきの顔画像をある程度は自動で拾える。** ただし経路ごとに強さが違う。

| 出どころ | 確実さ | 中身 |
|---|---|---|
| **話者チップの真上の2Dバストアップ**（画像4・10） | **高** | チップ基準の決め打ちで切れて、直下のチップが名前そのもの。ほぼ確実に対になる |
| **顔が1つだけ検出された ADV スクショ** | **中**（提案止まり） | 話者名が読めていて顔が1つなら、その顔＝話者の公算が高い |
| **カードストーリーのヘッダの丸アイコン**（画像2） | **低**（出れば儲けもの） | **そのストーリーが当該キャラ専用のときにしか出ない**。親愛度のヘッダには無い。中身もカードのアートワークのトリミングで、正準的な顔とは限らない |

**この自動採取には偏りがある。** 2Dバストアップが出るのは**3Dモデルを持たないサブキャラ側**
（話者チップが無彩色だった香名江・撫子）。つまり**メインのアイドルの3D形態には、この経路が効かない**。
いちばん枚数が多いところが手薄になるので、そこを埋めるのが真ん中の行。

ただし「顔が1つ＝話者」は**そのままでは間違える**。画像3がまさに反例で、
喋っているのはプロデューサー（`2943`）なのに、写っている顔は別のキャラ。条件を絞る:

- 話者チップが**有彩色**（＝プロデューサーでもサブキャラでもない）
- 顔の検出数が**ちょうど1つ**
- **2Dバストアップが出ていない**

これで大半は当たるが、切り返しのカット（Aが喋ってBが写る）はどうやっても混ざる。
→ **確定させず「この顔＝ことね？」の提案として要確認キューに出す。** 1タップで確定できれば十分速い。

- ヘッダアイコンは**表情が固定**なので、いずれにせよ表情の教師にはならない。キャラ専用。
- 手タグの初期コストは**表情のぶんと、メインアイドルの3D形態のぶん**。各表情5枚から始める。
- 「要確認」キューは**この1枚だけを大きく出して、候補チップを並べる専用画面**にする。
  スワイプで次へ。数十枚を数分で捌ける形にしないと、学習データが溜まらない。
- キャラは**話者名 OCR と上の自動採取がある分、最初から当たる**。表情は完全にこのループ次第。

### 4. キャラは「話者」と「写っている人」を分けて持つ

同じではない。画像4は**手前の2D立ち絵の側が喋っていて、奥の3Dモデルも写っている**。
画像1は**誰も喋っていないが2人写っている**。

```ts
speakerId:     CharacterId | null   // 誰が喋ったか（話者名 OCR。ほぼ確実）
characterIds:  CharacterId[]        // 誰が写っているか（顔照合 + 話者から補完）
```

- 検索では「ことねが写っている」と「ことねが喋っている」を**別々に絞り込めるようにする**。
- **複数人が写るのが常態**なので `characterIds` は最初から配列前提。
  「2人以上が写っている絵」「AとBが一緒に写っている絵」も絞り込めるようにする。
- **同じキャラに3Dモデルと2Dバストアップ立ち絵の2形態がある。**
  顔を切って埋め込む流れ自体は共通でよいが、**質感が別物なので kNN は形態ごとに教師が要る**。
  顔ごとに `form` を持たせ、タグ付け画面で
  「このキャラの2D立ち絵はまだ2枚しかラベルがない」を出せるようにする。
- 2D立ち絵は**話者チップの真上に left-align でアンカーされる UI 要素**（画像4・10で同じ位置）。
  シーンに自由に配置されるキャラではないので、**チップ基準の決め打ちで切り出せる**。
  一般的な顔検出に頼る必要がない、いちばん確実なルート。
  そして**喋るために出てくる**ので、話者名がそのままラベルになる（§3の自動採取）。
- **顔が写っていない人がいる。** 画像6・7の手前は完全な後ろ姿、画像9の手前は大きくボケている。
  顔検出は当然これを拾えない。ここは：
  - 髪色・髪型・シルエットは十分に特徴的なので、**顔でなく「その人の領域」を切れば CLIP は識別できる**
  - ただし領域を自動で切る手段がない（人物検出まで積むのは重い）
  - → **手で枠を足して名前を付ける動線**を用意し、その枠も学習データに入れる。
    「後ろ姿のことね」も溜まれば当たるようになる
- `characterIds` は**顔の数と一致しない**。顔0個でも人は写り得るし、話者から補完もする。
  「自動で確定した人」と「手で足した人」を区別できるようにしておく。

### 5. 名簿は「分かっている名前を種に、OCR から育つ」

**OCR で読めた話者名が、そのまま名簿の候補になる**。そのうえで、分かっている
主要キャラの名前は最初に種として入れておく（`profiles/gakumas.ts` の `knownNames`）。

- 既知の名前に**編集距離が近ければ既存に寄せる**（OCR のゆれを吸収）。
- **話者チップの色がキャラ固有の手がかりになる。** 実測では
  ことね＝黄〜桃のグラデ、清夏＝黄緑〜緑のグラデ、撫子＝紫、香名江とプロデューサー＝無彩色。
  チップから数ピクセル拾って平均色を取るだけなので**ほぼタダ**。
  - OCR が名前を読み違えたときの**照合の裏取り**に使う（色が合わなければ候補を疑う）
  - **無彩色かどうか**で「メインのアイドル」と「サブキャラ／プロデューサー」がおおよそ分かれる。
    2Dバストアップが出るのは後者側なので、形態の推定にも効く
  - 色は名簿の `color` にそのまま入れて、UI のチップ色にも流用する
- 遠ければ**新規キャラとして仮登録**し、「新しい名前が出ました」と提示。ユーザーは統合か改名かを選ぶだけ。
- 別名（`ことね` / `藤田ことね`）を1人にぶら下げられるようにする。
- プロデューサー名（画像3の `2943`）も1エントリとして扱えば、**自分のセリフだけ除外**もできる。

これでゲーム側のキャラ追加に**アプリ更新なしで追随できる**。

**種を入れる理由。** 育つ仕組みだけでは、1〜2 文字の名前が持たなかった。
名前の長さで許す食い違いを変えている都合上、2 文字までは完全一致しか認めない
（「清夏」と「千奈」は別人なので緩められない）。種が無いと、正しく読めた回の
綴りが初代になり、誤読するたびに別人が増えていく。実測でも「広」が「リム」と
読まれて仮登録された。種があれば、正しく読めた回は確実にその人に当たり、
誤読は名簿の画面でその人へ寄せられる（寄せた綴りは別名として残るので、
次から同じ誤読は当たる）。

種は**一覧が増えたときだけ**入れる（`Settings.rosterSeed` に一覧の長さを控える）。
毎回入れ直すと、名簿の画面で消した人が起動のたびに戻ってくる。
すでに同じ名前の人がいれば増やさず、仮登録を「確かめ済み」に変えるだけにする。

**すでにいる名前への改名は、まとめる。** 種を入れたので、誤読を直す操作は
必ず「すでにいる名前を打つ」形になる。そのまま名前を書き換えると同じ名前が
2 人並び、絞り込みが割れる。改名の欄には名簿の名前を候補として出し、
既存に当たったときは統合の経路に流す。

**0 枚の人は絞り込みに出さない。** 名簿が 20 人を超えたので、全員をチップにすると
「押しても必ず 0 件」のチップが並んで使う人が埋もれる。絞り込みは出てくる人だけ、
よく出る順に。爆速タグ付けの「写っている人」は畳んでおく（表情のチップが
画面から押し出されるため）。並びは名簿の順のまま変えない ── 枚数順にすると
振るたびにチップの位置が動く。

### 6. 検索は「OCR が汚い」前提で作る

`media-vault/src/lib/search.ts` の方針（NFKC 正規化・大小無視・空白無視のフォールバック）を土台に、
日本語 OCR 特有のゆれを足す：

- **長音のゆれ**: `ー`（長音）/ `一`（漢数字一）/ `-`（ハイフン）/ `─` を1つに寄せる
- **字形が近い誤読**: `力`↔`カ`、`口`↔`ロ`、`二`↔`ニ`、`工`↔`エ`、`八`↔`ハ` を同一視
- **濁点の分離**: `か゛` → `が` に結合（NFC 正規化で吸収）
- **記号の除去**: `…` `・` `、` 等を無視して照合するフォールバック

検索対象は **本文 / 話者名 / ヘッダ（作品名・話数）/ 自由タグ** の全部。
ヒット箇所はスニペットでハイライト（`media-vault` の `Highlight` / `buildSnippet` を流用）。

**絞り込みはファセット**で重ねる：キャラ（写／話）・表情・ストーリー種別・話数・お気に入り・期間。
数百枚なら全件走査で 1ms 未満。インデックスは張らない。

### 7. LINE 送信 — 共有シートに渡すまでの段取り

```
グリッドで長押し → 選択モード
   ↓
候補をタップで足していく（下部にトレイでサムネが並ぶ）
   ↓
[LINEに送る] → navigator.share({ files })  → OS の共有シート → LINE
```

実装上の勘所：

- **`share()` はタップと同じターンで呼ぶ**。`await` を挟むと iOS で「ユーザー操作由来」と見なされず弾かれることがある。
  → **選択した時点で `File` を作っておく**。送信タップ時にはもう配列が手元にある状態にする。
- **`files` と `text` の同時指定は iOS で不安定**。既定は `files` のみ。
  セリフは別ボタンで**クリップボードにコピー**（LINE に貼る用）。
- **枚数が増えると共有シートが重い**。10枚を超えたら分割を促す。
- フォールバック: 1枚ならクリップボードに画像コピー（`ClipboardItem`）、それも不可ならダウンロード。
- PC からは共有シートが使えないので、**クリップボード経由**が主動線になる。

## データモデル

```ts
type ShotId = string          // ULID（時系列で並ぶ）
type CharacterId = string
type MoodId = string

interface Shot {
  id: ShotId
  createdAt: number           // 取り込み日時
  shotAt?: number             // File.lastModified から推定（iOS 写真経由だと EXIF は落ちがち）
  fileName: string
  mime: string
  size: number
  width: number
  height: number
  layout: 'portrait-adv'         // ヘッダ＋パネル＋バー
        | 'portrait-adv-nopanel'  // セリフのない「間」。ヘッダは読める（画像8）
        | 'portrait-plain'        // UI 非表示（画像1）
        | 'landscape-story'       // 横・字幕（画像5,6,7）
        | 'unknown'
  ui: { header: boolean; panel: boolean; bar: boolean }   // 3要素を独立に持つ
  dhash: string               // 重複検出

  // --- テキスト ---
  body: string                // 本文（OCR または手入力）
  speakerRaw?: string         // 話者名の OCR 生値
  speakerChipColor?: string   // 話者チップの平均色。キャラ照合の裏取り／無彩色ならサブキャラ
  speakerId?: CharacterId     // 名簿に寄せた結果
  headerRaw?: string          // 「親愛度 第24話」「冠菊 1話」
  story?: {
    kind: '親愛度' | 'カード' | 'メイン' | 'イベント' | 'その他'
    title?: string
    episode?: number
  }
  textEdited: boolean         // 手で直した → 再OCRで上書きしない

  // --- 人物 ---
  faces: Face[]               // 顔枠＋埋め込み＋推定
  characterIds: CharacterId[] // 「写っている」確定値
  charactersEdited: boolean

  // --- 分類 ---
  moods: MoodId[]             // 複数可（ドヤ顔 かつ 楽、はある）
  tags: string[]              // 自由タグ
  favorite: boolean
  moodsEdited: boolean

  // --- 自動判定の控え ---
  suggest?: {
    characters?: { id: CharacterId; score: number }[]
    moods?: { id: MoodId; score: number }[]
  }
  status: { ocr: Status; embed: Status }   // 'queued' | 'processing' | 'done' | 'error'
  error?: string
}

interface Face {
  box: { x: number; y: number; w: number; h: number }  // 画像幅・高さに対する比率
  source: 'auto' | 'manual'
  form?: '3d' | '2d-bust' | 'header-icon' | 'body'
                              // body = 顔が写っていない人に手で付けた領域（後ろ姿・ボケ）
                              // header-icon = ヘッダの丸アイコン。キャラ専用ストーリーのときだけ出る
  occluded?: boolean          // ガラス越し・見切れ・ボケ。信頼度を下げる材料
  vectorId?: string           // vectors ストアへの参照
  characterId?: CharacterId   // この顔が誰か（確定値）
}

interface Character {
  id: CharacterId
  name: string                // 表示名
  aliases: string[]           // OCR ゆれ・略称・フルネーム
  color?: string              // チップの色
  isProducer?: boolean        // 自分。除外フィルタ用
}
```

### IndexedDB のストア分割

| ストア | 中身 | 読み方 |
|---|---|---|
| `shots` | 上記メタ（Blob を含まない） | 起動時に**全件メモリに載せる**。数百件 × 約1KB＝数百KB |
| `blobs` | 原本画像 | **絶対に一括で読まない**。詳細表示・送信時のみ |
| `thumbs` | サムネ（幅400 WebP、約10KB） | 表示中のカードだけ遅延読み込み |
| `vectors` | CLIP 埋め込み（Float32Array 512次元＝2KB） | kNN 用に全件メモリ |
| `characters` | 名簿 | 全件 |
| `settings` | 保存形式・最終バックアップ日時など | — |

`media-vault` はサムネをメタに同梱しているが、**ここでは分ける**。
枚数が増えたとき「一覧を開いた瞬間に全サムネがメモリに乗る」のを避けるため。

## モデルの選定と、その代償

| | 採用 | ダウンロード | iPhone での1枚あたり | 備考 |
|---|---|---|---|---|
| OCR | tesseract.js jpn+eng | 約25MB（自前配信） | 0.5〜2秒 | 全画面ではなく切り出した帯だけ渡すので速い |
| 埋め込み | CLIP ViT-B/32（uint8量子化） | 約40MB | 0.3〜1秒 | 「軽量モード」として MobileNet 級（約10MB）も選べるようにする |
| 顔検出（Phase 4） | アニメ顔検出 ONNX（yolov8n級） | 約10MB | 0.3〜0.8秒 | 1枚から複数の顔を拾う。小さい顔・見切れ・2D立ち絵まで拾えるかが要検証 |

**GitHub Pages は COOP/COEP ヘッダを設定できない** → `SharedArrayBuffer` が使えず、
**WASM はシングルスレッド**で動く（既存アプリと同じ制約）。SIMD は効くので致命傷ではないが、
**バッチ処理は「数百枚で数分」かかる**前提で、進捗表示と中断・再開を用意する。

## 実装フェーズ

### Phase 0 — 足場と「消えない」保証 ✅
`/shot-bank/` に Vite + React + TS、Pages 配信、トップページへの導線。
IndexedDB（`shots` / `blobs` / `thumbs` / `kv` の 4 ストア）、取り込み（複数選択・ドロップ・ペースト）、
JPEG 再エンコード、サムネ、グリッド表示、削除。
PWA（manifest + Service Worker）とホーム画面追加の案内、ZIP バックアップ／リストア、容量表示。
dHash による重複検出もここに入れた（同じスクショの二度取りは実際に起きるので、
取り込みの一部として最初から要る）。

実測 10 枚で確認済み: 取り込み 31.9MB → 3.0MB、同じ 10 枚の再取り込みは全件が重複として弾かれ、
ZIP 書き出し → 全消去 → 復元で 10 枚が戻る。
→ この時点で「ただのローカル画像アルバム」として既に使える。

### Phase 1 — 文字認識とテキスト検索 ✅
パネルの検出（左右の余白の平坦さ）、話者名チップの実測、ヘッダの OCR 判定、
領域ごとに変えた二値化、tesseract（jpn+eng、資材は自前配信）で本文・話者名・ヘッダを読む。
ゆれ吸収検索、ヒットのハイライト、手修正、再OCR、取り込み時の自動読み取り。

**実測 10 枚での結果**

| | 結果 |
|---|---|
| レイアウト判定 | **10/10 正しい**（縦ADV 5・パネルなし ADV 1・UI なし 1・横 3） |
| 話者名 | **5/5 読めた**（ことね / 2943 / 香名江 / 清夏 / 撫子） |
| 本文（縦 ADV） | 5 枚中 4 枚がほぼ完全。1 枚は「…」の連なりで崩れる |
| ヘッダ（話数） | 6 枚中 5 枚で話数が読めた |
| 横の字幕 | **読めない**。縁取りの白字が絵の上に乗るので崩れる |

**領域ごとに二値化を変えた。** 文字の出方が 3 通りあるため。
本文は明るい地に暗い字（大津の方法）、話者チップは白字と黒字の両方がある
（大津の方法で少数派を字とみなす）、ヘッダは半透明の暗いチップに白字（明るい上位から切る）、
横の字幕は縁取りの白字（近くに暗い画素があることを手がかりにする）。

**読めなかったものは残さない。** 横向きの話者名は実測で
`-MEAowFel"elNR4|oieeAoF職リーサビ1` のような文字列になった。
そのまま保存すると検索の邪魔にしかならないので、もっともらしい字の割合で足切りして捨てる。
空にして手で入れてもらうほうがまし。

→ **要求「テキスト認識と検索」がここで満たされる（横向きを除く）。**

### Phase 2 — 名簿とタグ、爆速タグ付け ✅
話者名 → 名簿の編集距離照合、新規キャラの仮登録・統合・改名・別名。
表情タグ（初期セット：喜 / 怒 / 哀 / 楽 / 照れ / 驚き / はてな / ドヤ顔 / ドン引き / ジト目 / 真顔 / 泣き / 決め顔）と自由タグ。
ファセット絞り込み、スワイプで次々タグを振る画面。

**実測 10 枚での結果**

| | 結果 |
|---|---|
| 名簿の自動生成 | 読み取れた 5 人が仮登録された（清夏 / 2943 / 香名江 / 撫子 / ことね） |
| チップの色 | **5/5 取れた**。清夏 `#92de5a`、ことね `#f7d81e`、撫子 `#545365`、プロデューサーとサブキャラは無彩色 `#978d83` |
| 誤読の直し | 「理名江」を「香名江」に改名すると、**元の綴りが別名に残る**。次からは編集距離に頼らず当たる |

**「チップの色はキャラ固有」が裏付けられた。** 見込んだとおり、メインのアイドルは有彩色、
プロデューサーとサブキャラ（2D立ち絵で出る側）は無彩色に分かれた。
名前照合の裏取りに使っている ── 字が 1 字違いでも色が大きく食い違えば別人とみなす。

**名前の長さで許す食い違いを変える。** 2 文字までは完全一致だけ（「清夏」と「千奈」は別人）、
3〜5 文字なら 1 字、6 文字以上なら 2 字まで。
Phase 1 で「香名江」が「理名江」と読まれて検索に当たらなかった件は、これで拾える。

**タグ付けの画面では、画像の高さを決め打ちにした。** 画面に合わせて伸び縮みさせると、
読み込みが終わった瞬間にタグの位置が動く。タップしようとした先が動かないことのほうが大事。

**その上限は % ではなく実寸で書く。** grid + `max-height: 100%` で組んでいたら、
実機（iOS Safari）で**縦長のスクショだけ**が枠より 234px 下にずれ、タグの上に重なった。
行の高さを「画像の本来の高さ」で取ってからその中央に置いた場合と 1px 差で一致したので、
% の解決先が枠でなく行になっていたと見られる。Chromium では再現しない。
`calc()` の実寸に直し、枠に `overflow: hidden` を足して、ずれてもタグの上には出ないようにした。

→ **要求「キャラで絞り込み」が満たされる。表情は手タグで満たされる。**

### 実機で出た読み取りの取りこぼし（Phase 1・2 のあとの直し）

実機のスクショ 3 枚で、手元の 10 枚では出なかった壊れ方が 3 つ出た。

| 症状 | 原因 | 直し |
|---|---|---|
| 本文にチップの文字が混ざり、話者名が化ける | 明るさだけで見ていたので、チップの行がパネルの行と区別できず、帯が上へ伸びていた | 左右の余白の **色** の距離で行を見る。実測でパネルの行は色差 60 以下、チップの行は 169 以上と、明るさでは分かれないものが色では分かれた |
| 話者名が空になる（「清夏」→ `"|B="`、「広」→「リム」） | 切り出しがチップの左端から始まっていた。角が丸いので、後ろが暗いと縁が**上から下まで真っ黒な柱**として入る。柱は字より背が高く、1 行の高さを柱が決めてしまう | 色を採る種と同じだけ内側から切り出す。右端は動かさない |
| 全角の「｜」が名前に混じって名前ごと捨てられる | 記号の除去を NFKC の前にやっていた | 先に NFKC で揃える |

切り出しは、二値化のあと**字の外接矩形まで詰めてから**渡すようにした。
話者チップは幅を決め打ちにしているので、短い名前だと右の 7 割が白紙のまま残る。

実機の 1 枚（3679x8000、ことね）を 11 枚目の見本として置いた。これまでの 10 枚では
どれも再現しなかった「帯が上へ伸びる」を再現する唯一の絵で、これを外すと色の距離の
直しに回帰テストが無くなる。JPEG のまま置いてある（PNG に直すと 27MB になるうえ、
元の画素を保つほうが回帰として意味がある）。画素数が 9 倍あるので、
画素数に依った定数が紛れ込んだときにもここで露見する。

### 読み取った文字は、保存する前に読める形にする

実機で「誤字が多い」と言われて中身を見たら、字を読み違えているものと、
**後処理をしていないだけ**のものが混ざっていた。後者は保存する側で直せる。

- **日本語の字間の空白を詰める。** tesseract は日本語の字間に空白を撒く
  （実測:「それ は そっ うっ 。」）。検索は空白を落としてから照合するので当たって
  いたが、画面にはそのまま出るし、LINE へ送るときも付いてくる。落とすのは
  **少なくとも片側が日本語**の空白だけ。英字のあいだの空白は語の区切りなので残す。
- **端の短いゴミを落とす。** 本文の箱にはパネルの飾りが入る（実測: 右下の「∨」が
  `NV`、左上の縁が `ON`）。日本語の本文の端で、日本語も数字も含まない 3 文字までの
  塊は字ではない。4 文字以上は、読み違えた本文であるほうが見込みが高いので残す。
- **題の長音を削らない。** 題の前後のゴミを落とすつもりで中まで削っていて、
  「ハッピーミルフィーユ」が「ハッピミルフィユ」になっていた。削るのは端だけにする。
- **題は「重みのある字」で数える。** 長音と小書きの仮名は字数を稼ぐが、題を名指す
  力は弱い。実測で「親愛度」が「にーー衝」と読まれ、見かけの 4 字で題として通って
  いた（重みで数えれば「に衝」の 2 字）。英数字だらけの塊も題にしない
  （実測「V4REE第」）。

**弾いたものは、弾いたと分かるようにする。** 名前として受け取れなかった読み取りを
黙って空にすると、「読めなかった」のか「読めたが名前と認めなかった」のか分からず、
直しようがない。弾いたときだけ生値を残して、詳細の画面で見せる。

### 切り出しは詰めない

字の外接矩形まで詰めてから渡すほうが素直な絵になると考えて一度やったが、
**実測で悪くなった**。チップ 10 枚（手元 6 + 実機 4）を Node の tesseract で読ませて、
詰めない 10/10、詰める 7/10。「リーリヤ」が「リーリヤギヤ」に、「撫子」が「撫子.」になる。
実機で出ていた「リーリヤギヤ」は、この詰めが作っていた。
まわりの余白は、行の高さを測るための手がかりになっているらしい。

### 本文の箱に、チップの下の縁を入れない

話者チップはパネルの上端をまたぐ。本文の箱を「パネルの上端＋6%」から始めていたので、
チップの下の縁が 1 行ぶん入り、それが字として読まれていた
（実測: 切り出しの上端に横棒が並び、本文の頭に「いび」が付く）。
チップの位置は分かっているので、その下端より下から始める。

### 名前が読めないときは、チップの色で当てる

読み取りは同じ絵でも当たり外れがある。**同じ「星南」の切り出しが、
Node では「星南」、開発環境の Chromium では "Em" になった**（どちらの絵も人が見れば読める）。
字が崩れても**チップの色は変わらない**ので、こちらは崩れない手がかりになる。

寄せ方は 3 周に分ける。

1. **名前で当てる。** ここで、当たった人の色を覚える。
2. **名前は読めたが誰にも寄らなかったもの。** ここも色を見る（下の「誤読は
   本人に吸わせる」）。色が 1 人を指せばその人のものにし、指さなければ
   新しい人として仮登録する。
3. **名前が読めなかったものを、色で当てる。** 名簿が出そろってから見るので、
   「近い人が 2 人いる」をきちんと弾ける。

色だけで決めるときの許しは 30 にする。実測でいちばん近い 2 人は
星南 `#ffb03d` と千奈 `#f08326` で距離 45。裏取りに使う 60 のままだと両方に当たる。
**当てはまる人がちょうど 1 人のときだけ**返す。

読めた回が 1 度もないキャラには効かない（色をまだ覚えていないため）。
枚数が増えるほど当たるようになる。

### 色は種として持たせる。ただし 1 色では足りない

主要キャラ 20 人ぶんのチップの色を、実測して種に入れた。名前が一度も読めない
キャラでも最初から色で拾える。

値は**原寸のスクショ 14 枚**を speakerChipColor に通した実測。チップ高はどれも
画像高の 2.29〜2.52% に収まっていて、検出がはみ出した枚は 1 枚も無い。

**縮小した絵からでも同じ値が採れる。** 先に 1/4 の連結スクショで測っていたが、
原寸で測り直したら差は 0〜5 だった（リーリヤ 0、清夏 0、広 5）。
壊れるのはチップの縦の検出がはみ出した枚だけで、それは高さで見分けられる
（正常は 2.3〜2.8%、はみ出した枚は 3.79%）。
はみ出したら捨てずに**打ち切る** ── 上端は当たっているので、そこから決め打ちの
高さを取るほうが色がよく採れる。

**色は場面で動く。** 星南は明るい稽古場で `#ffad28`、暗い舞台袖で `#ffb03f` と 23 離れた。
1 色に決め打つと片方の場面で当たらない。だから**何色でも覚える**（`colorSamples`）。
すでに近い色を知っていれば増やさないので、場面ごとに違う色だけが溜まる。
星南は 2 色とも実測できたので、種の時点で 2 色持たせてある。

**許容は 15。** 無彩色を除いていちばん近い 2 人は千奈 `#ff8a20` と星南 `#ffad28` で
距離 35、次が手毬 `#25b4eb` と広 `#00bed8` で 37。30 のままだと、片方の色が少し
動いただけで隣に届いてしまう。同じ人の同じ場面での揺れは実測でごく小さい
（ことね 6、リーリヤ 1、広 1、清夏 0）ので、15 なら同じ人は拾えて隣とは 20 以上あく。

**無彩色の人は色では見分けられない。** 香名江・プロデューサー・月花・四音・燐羽・優は
どれも `#988d83` で、実測でも距離 0。「当てはまるのがちょうど 1 人」を満たせないので
色の仕組みは働かない。これは正しい動き（誤爆しない）だが、この人たちは名前が
読めるかどうかに頼るしかない。

**ライバル勢は濃い色。** 撫子のチップは濃く（実測 `#535365`、チップ高 2.33% で
検出は正常）、白抜きの字が乗る。あさり先生のグレー `#988d83` とは距離 69 で、
はっきり別の色。撫子・月花・四音・燐羽はライバルなので、この 4 人が濃い側らしい。

**実測できたのは撫子だけ。だから 4 人まとめて同じ色にする。** 撫子ひとりに濃い色を
持たせると「当てはまるのがちょうど 1 人」を満たしてしまい、**濃いチップが必ず
撫子に当たる** ── 月花・四音・燐羽の枚が丸ごと撫子になる。当てないより悪い。
4 人を同じ色にしておけば必ず 2 人以上に当たって諦める。1 人ずつ実測できたら分ける。

推測が外れていても損はしない。仮に 3 人が本当はグレーだったとしても、グレー側は
優・香名江・あさり先生の 3 人で決められず、濃い側は 4 人で決められない。
どちらに転んでも「当てない」に倒れる。**取り違えだけは起きない。**

なお実測できているグレーも**あさり先生 1 人ぶん**で、優と香名江は
「あさり先生と同じ」から入れた値。

### ライバル 4 人は実測でも同じ色だった

月花・四音・燐羽の実機スクショをもらって測った。

    月花   #535365   チップ高 2.33%
    四音   #535365   チップ高 2.33%
    燐羽   #535160   チップ高 2.24%
    撫子   #535365   チップ高 2.33%

4 人とも同じ。**分ける必要はない**（いちばん離れている燐羽でも撫子と距離 4）。
まとめて置いた判断はそのままでよく、この 4 人は名前が読めた回だけ拾える。

### 種は 1 点に賭けない

燐羽の 1 枚（1408x3040）で、チップを丸ごと外していた。色が本文パネルの
生成り `#fdf7e3` になり、名前の切り出しも本文を指していた。

原因は種の置き方。チップの下端とパネル上端のあいだの隙間は**機種で変わる**
（実測 1206x2622 で画像高の 0.84%、1408x3040 で 1.09%）。種はパネル上端から
決め打ちで 1.0% 上に置いていたので、隙間の広い機種では **3px だけ下に落ちて**
隙間に着地し、隙間と地続きの本文パネルを測っていた。

画像 7 枚で「色が合って、かつ高さが測れる」種の位置を実測すると
**0.0105〜0.0165 の 0.6pp しかない**。決め打ちの 0.010 はその窓の外で、
手元の画像でたまたま当たっていただけだった。中心へ寄せても窓は 0.6pp のままで、
次の機種でまた外れる。

だから 1 点をやめ、0.006〜0.030 を 0.002 刻みで試して
**いちばん多くの種が同じ上端に収束した帯**を採る。

「もっともらしい最初の 1 つ」ではいけない。チップの下にたまたま同じくらいの
高さの帯があると、そちらを先に掴む（実測: 画像 04 は下へ 1px ずれただけで外れた）。
本物のチップは中に種を何行も置けるので票が集まる。まがい物は薄いので票が割れる。

実測（パネル上端を上下にずらして、正しい色にたどり着く幅）:

    画像 02   -33〜 72px  4.00pp
    画像 03   -39〜 74px  4.42pp
    画像 04   -36〜 47px  3.17pp   ← 直す前は下へ 0px も耐えなかった
    画像 09   -27〜 96px  4.69pp
    画像 10   -33〜 78px  4.23pp
    画像 11  -108〜200px  3.85pp
    画像 12   -72〜 59px  4.31pp   ← 直す前は外していた枚

いちばん狭いところで 3.17pp。1 点決め打ちのころの 0.60pp から 5.3 倍。

### 種の色は、あとから直せないといけない

上の値は実測して少しずつ直している。ところが種は **色を持っていない人にしか
入れていなかった**ので、直した値がすでにある名簿には一生届かなかった。
撫子が濃いと分かっても、手元のアプリは古い色を持ったまま。

種が前に書いた色は、種が入れ直せるようにする（`withSeedColor`）。
上書きしてよいのは、**学習が `color` を書き換えないから**
（`withColorSample` は `color` が空のときだけ入れ、あとは `colorSamples` に足す）。
それでも実物のチップから覚えた色である可能性は残るので、**捨てずに見本へ移す**。
近い色は移さない ── 同じ色が 2 つ並んでも当たり方は変わらない。

見本が増えても危なくない。色が増えるほど「当てはまる人」が増え、
2 人以上なら諦めるので、**取り違えではなく取りこぼしの側に倒れる**。

実測（v3 の名簿に v4 の種を入れ直す）:

    v3     月花 #988d83 / 撫子 #545365      濃いチップ → 撫子（取り違え）
    v4     月花 #535365（見本 #988d83）      濃いチップ → 当てない
           撫子 #535365                      「月花」と読めた回 → 月花

### 誤読は本人に吸わせる。仮登録は色の数に入れない

実機で **広と莉波だけ、読めるときと読めないときがあった**（清夏は直っていた）。
名簿を見ると「広上」という仮登録がいて、**広と同じ水色**を持っていた。
以前は「莉波回生前」がいた。

色で当てる仕組みは「当てはまるのがちょうど 1 人」が条件なので、
**同じ色の人が 2 人になった時点で、本人の枚も丸ごと拾えなくなる。**
誤読が 1 人まぎれこむだけで、そのキャラの色の手がかりが死ぬ。

直し方は 2 つ。

**入れない。** 2 周目で仮登録を作る前に色を見る。色が 1 人を指すなら、
それは新しい人ではなく誤読とみなして本人に付ける。
誤読の綴りは別名に足さない ── 綴りは毎回ちがうので、溜めても次に当たらないし
名簿が汚れるだけ。

これは「2 周目を色に頼らせてはいけない」を覆すように見えるが、覆していない。
プロデューサー（2943）が香名江に吸われないのは、**無彩色の人が 6 人いて
必ず 2 人以上に当たるから**。当時は 6 人ぶんの種が無く、香名江ひとりが
グレーを持っていたので吸われた。種が揃った今は素通りする。

**数えない。** `findByColor` は**仮登録の人を数に入れない**。
すでに取り込んだぶんに「広上」が残っていても、水色は広ひとりを指したまま。
全消しして入れ直さなくても直る。色は強い手がかりなので、確かめた人にだけ使う。

### 色は、手で教えられるようにする

上の仕組みには穴がある。**名前が一度も読めないキャラは、色を覚える機会がない。**
実機で「清夏」がそうなった ── 84 枚のどれでも読めず、名簿の清夏には色が付かず、
だから色でも拾えない。自動だけでは抜け出せない。

詳細の画面に「話者を選ぶ」を置く。選ぶと、その人にこのチップの色を覚えさせ、
**その場で他の枚にも当て直す**（読み直しは要らない。要るのは色の対応づけだけ）。
見出しにチップの色を出しておく ── 何を覚えさせようとしているかが見えないと、
教えるほうも確かめようがない。

手で決めた話者には印を付け、以後の自動の寄せでは触らない。読み取りより人の判断のほうが確か。

名簿が 20 人を超えるので、選ぶ欄は畳んでおく。決まっていない枚だけ開いた状態で出す。

### 更新が届かないことは、それ自体が不具合

実機で、直したはずのものが何時間たっても届いていなかった（名簿に主要キャラが
入らず、全員が仮登録のままだった）。コードは正しく、**古いビルドが動き続けていた**。

ホーム画面のアプリはアイコンを押しても前の状態から再開することがあり、
新しいデプロイの index.html を取りに行かない。service worker を「HTML は網優先」に
してあっても、そもそも遷移が起きなければ効かない。

- ビルドの刻印を `version.json` としても配り、起動時と**画面に戻ってくるたび**に読み比べる。
  違っていたら「新しい版があります」を出し、押せば読み込み直す。
- 刻印は必ず網から取る（service worker で素通しにし、古い版に掴まれないよう
  URL に時刻を付ける）。ここをキャッシュされると、気づくための口が塞がる。
- 種入れは初回に 1 度しか走らないので、**自分で入れ直せる口**を名簿の画面に置く。
  仕組みが動かなかったときに、待つ以外の手を残しておく。
- **旗だけを見ない。** 全消しはスクショと名簿を消すが設定は消さないので、
  「もう入れた」の旗が立ったまま名簿が空になる。実機で、全消し → 入れ直しのあと
  種入れが飛ばされていた（実測）。名簿が空なら、消した人を蘇らせる心配もないので
  入れ直してよい。旗ではなく実態を見る。

### 名簿から、その人の枚へ

名簿は「誰がいるか」の一覧なので、そこから中身へ行けるのが素直。
名前を押すと、その人が**話者としても「写っている人」としても**出ている枚を開く。
0 枚の人は押せない（押しても必ず 0 件なので）。

**開き方は「一覧に絞り込みを掛けて閉じる」ではなく「一階層潜る」。**
絞り込みにして閉じてしまうと、名簿へ戻る道がなくなる（実機で指摘された）。
名簿のシートの中で開けば、左端からのスワイプでそのまま名簿へ戻れる。
潜った先からスクショを開いたときは、詳細を名簿より前の層に出す
（どのシートも同じ層なので、並び順だけだと後から書いたほうが前に来る）。

### 「同じ絵がある」は、アプリが決めない

取り込み済みと同じ絵は黙って飛ばしていた。だが同じに見えても、撮り直したほうが
綺麗だったり、逆に取り込み済みのほうにタグが付いていたりする。
**どちらが要るかはアプリには分からない。**

両方を並べて見せて、4 通りから選んでもらう ── 取り込む絵を残す / すでにある絵を
残す / 両方残す / 両方消す。すでにあるほうには、大きさ・話者・タグの数を添える
（見た目が同じでも、持っているものが違う）。縦長のスクショを 2 枚並べるので横に割る。
縦に積むと片方が画面外へ出て、比べるという肝心のことができない。

毎回訊かれたくない人のために、設定で切れる（切ればこれまでどおり黙って飛ばす）。

### 仮登録は「この周で作った人」にも当て直す

名簿に無い名前が何枚あっても、増えるのは 1 人でなければならない。
寄せ方を 3 周に分けたとき、2 周目（仮登録）で **その周に作った人を見ていなかった**。
実機で 84 枚から名簿が 40 人になり、全員が 1 枚だった
（同じ「ことね」が 13 人、「2943」が 3 人）。
名簿が壊れると、色で当てる仕組みも道連れになる ── 同じ色の人が何人も並ぶので、
「当てはまるのがちょうど 1 人」の条件を満たせなくなる。

### 全消しのあとは、その場で種を入れ直す

種入れは起動時にしか走らないので、全消ししてそのまま取り込むと名簿が空のまま始まる。
実機で、全消し → 再投入のあと主要キャラが 1 人も入っていなかった。
消した直後に入れ直す。

### 一覧は「誰が何を言ったか」を出す

サムネだけでは、どの 1 枚かを絞り込めない。話者（名簿の色つき）とセリフを
タイルの下に 2 行まで出す。行数を決め打ちにしないと、タイルの高さが揃わず段がずれる。
セリフの折り返しはつないだあと空白を詰め直す ── そうしないと折り返しの跡が
「〜って、 そう言って」のように空白として残る。

**なお、読み取りエンジンの当たり外れは環境で変わる。** 同じ PNG・同じ言語データ・同じ
wasm コアでも、Node では「清夏」と読めるものが、この開発環境の Chromium では `|B=` になった。
実機（iOS Safari）は Node 寄りの結果を返す（ヘッダの「親愛度 第32話」は実機では読めていた）。
**だから Chromium の結果に合わせて設定を詰めてはいけない。**
直すべきは「渡す絵から文字でないものを取り除く」ほうで、それはどの環境でも効く。

### Phase 3 — 候補一覧から LINE へ ✅
選択モード、選択トレイ、`navigator.share({ files })`、セリフのテキストコピー、
枚数・総量の但し書き、ZIP のフォールバック。
→ **要求「候補一覧から LINE 送信」がここで満たされた。**

**送り口は共有シートひとつ。** LINE へ直接投げる API は個人のページからは叩けないし、
叩けたとしても宛先を選ぶのは結局ユーザなので、OS の共有シートに渡すのがいちばん短い。
iOS なら共有先に LINE が並ぶ。

**送るのは画像だけ。title も text も付けない。** ここは読み違えていた。
`navigator.share` に付けた文字列は落ちるだろうと思って title に「3 枚」と入れていたが、
**実機では LINE がそれを本文として 1 通そのまま送っていた**（ユーザ報告）。
送り先はトークなので、要らない一言はそのまま相手に見える。

**だから「送る」と「セリフをコピー」を分ける。** セリフを常に付けると、要らないときも
相手のトークに流れる。送るかどうかを決めるのは、受け取る相手を知っている人のほうがよい。

**共有シートが無い環境では ZIP に落とす。** 「送れません」で行き止まりにせず、
手で渡す道を必ず残す（PC のブラウザでは実際にこちらに落ちる）。
バックアップの ZIP とは別物にした ── あちらは戻すための manifest つき、
こちらは人に渡すためのただの画像の束。混ぜると渡した相手に要らない JSON が付いていく。

**ファイル名は「誰の何話か」にする。** `IMG_5922.PNG` は受け取った側に何も伝えない。
`月花-親愛度_第18話.jpg` なら LINE のトーク上でも見分けが付く。
名前も話数も分からない枚は日付（`20260901-0905.jpg`）にする。id は伝わらない。
同じ人の同じ話数は連続したセリフで普通に起きるので、重なったら連番を足す。

**枚数と総量を、送る前に出す。** 共有シートは枚数ではなく渡す総量で詰まることが多い
（スクショ 1 枚が 2〜4MB あるので 20 枚で 60MB を超える）。
**閾値（12 枚 / 50MB）はまだ実機で測っていない見当。** 止めはせずに但し書きを出すだけにして、
実機で詰まる枚数が分かったら合わせる。

**選ぶモードではタイルを開かない。** 同じ押下に「開く」と「選ぶ」の 2 つの意味を
持たせると、送るつもりが開いてしまう。開きたいときはモードを抜けてもらう。

**絞り込みを変えたら、見えていない枚は選択から外す。** 見えていないものを送るのは事故。

**一括の入口はヘッダに入れない。** 402px の画面では 6 つ目を足した時点で
題字と「取り込む」が 2 行に折り返した（実測）。
「タグを振る」と「選んで送る」は、どちらも「いま出ている枚」への操作なので横に並べた。

**1 枚だけ送る入口は、詳細の絵のすぐ下。** 上の帯はもう 4 つ（戻る・名前・★・削除）で
埋まっているし、「この 1 枚を送る」の判断は絵を見ている場所でするので、そこが近い。
逃げ道は ZIP ではなくその絵そのものを落とす ── 1 枚を渡すのに開いてもらう手間は要らない。

### 保存の名前は ASCII に寄せる。共有の名前はそのままでよい

**Chromium は `a.download` に ASCII 以外が 1 文字でも入っていると、名前ごと捨てる。**
拡張子まで消えて `download` になり、OS がその絵を開けなくなる。
実測（画面ありでも同じ。ヘッドレスのせいではない）:

    "ことね.jpg"         → "download"
    "kotone-ことね.jpg"  → "download"
    "café.jpg"           → "download"
    "a_b-c.jpg"          → "a_b-c.jpg"

名前と拡張子のどちらかを諦めるなら**拡張子を採る**。日付にすれば「いつ撮ったか」は
残るが、拡張子の無い絵は開くことすらできない。

**共有シートへ渡すぶんはこの制限を受けない**（File が名前を持っていく）ので、
`shareName` は日本語のまま、`downloadName` だけ ASCII に寄せる。
ZIP の名前（`shot-bank-20260901-0018.zip`）はもともと ASCII なので影響しない。
ZIP の**中身**の名前も影響しない ── `a.download` を通らないため。

### Phase 4 — 顔検出（自動分類の土台） ✅

**ONNX はやめて、lbpcascade_animeface（MIT、nagadomi 氏）にした。**
npm にアニメ顔専用の検出器は無く、汎用の顔検出（blazeface / face-api.js）は
実写で学習したもの。アニメ顔の実績で選べるのはこのカスケードだった。

**opencv.js は積まない。** LBP カスケードの評価器は 200 行ほどで書ける一方、
opencv.js は 10MB ある。この 1 つの機能のために配信物を 40 倍にする理由がない。
自前なら DOM を使わないので、実スクショでそのまま回帰も測れる。

原本の XML（241KB）は `vendor/` に置き、ビルドで数値の並びに畳んで配る
（87KB、gzip 40KB）。24x24 の窓・20 段・771 の弱識別器・642 の特徴。

**画像ではなく特徴のほうを拡大する。** LBP は升目どうしの大小しか見ないので、
面積で割る正規化が要らない（Haar と違って明るさの分散を測らない）。
だから画像のピラミッドを積み直さずに、積分画像 1 枚のまま倍率だけ変えられる。

**重なりの数で選り分ける。** 顔 1 つに何枚もの窓が通り、誤検出はぽつんと 1 枚しか
通らない。実測（見本 12 枚、目で数えた顔 19 個。後ろ姿は数えない）:

    minNeighbors   拾えた    余分
    1              19/19     20
    2              18/19      3   ← 余分は 3 つとも「重なり 2」ちょうど
    3              17/19      0   ← 採用
    4              16/19      0

**取りこぼしより誤検出のほうが痛い。** 見つけた枠は Phase 5 の学習に使うので、
顔でないものが混ざると母集団が汚れる。取りこぼしは手で足せば済む。
本物の重なりは 3〜28、余分は 2 ちょうど。きれいに分かれるので 3 を採った。

**まとめ方は推移的に閉じる。** 代表 1 つと比べるだけだと、同じ顔が入れ子のまま
2 つ 3 つ残った（実測: 1 枚の顔が 849px と 765px に分かれた）。union-find にする。

**予想どおりに拾えたもの・拾えないもの**

- 全身ショットで高さ 1〜2 割の顔（画像 08）… 2 人とも拾えた
- 話者チップの上の 2D 立ち絵（画像 04・10）… 拾えた。
  **ここが効く** ── (顔画像, 名前) の対が Phase 1 の時点でタダで採れる
- 完全な後ろ姿（画像 06 の 1 人）… 拾えない。顔の造作がどこにも無い

だから**顔枠を追加／削除／ドラッグ調整でき、顔でない領域にも名前を付けられる**動線を
同時に作った。これは「あると便利」ではなく、**検出が原理的に届かない範囲を埋める
必須の部品**。後ろ姿の人を数に入れるには、頭のあたりを囲んで名前を付けるしかない。

**枠は元画像の画素で持つ。** 表示のときだけ % に直す。絵の表示倍率は画面幅で
変わるので、画素のまま持たないと機種で意味が変わる。

**読み直しても手で直した枠は消さない。** 手で足した枠と、名前を付けた枠は残し、
自動のぶんだけ入れ替える。消えると直す気がなくなる。

**名前を付けた枠は「写っている人」に反映する。** 枠と `characterIds` を別々に
持つと必ずずれるので、枠のほうを唯一の出どころにして毎回組み直す。
話者は別扱い ── 喋っていなくても写っていることはあるし、その逆もある。

読み取りと同じ 1 枚から拾うので、画像のデコードは 1 回で済む。
**1 枚あたり約 2 秒**（実測、見本 12 枚の平均）。検出が落ちても読み取りは残す。

## 写真アプリから取り込む

**iOS の共有シートに Web アプリは出せない。** 共有先にアプリを並べる仕組み
（Web Share Target）は Android の Chrome だけで、Safari は実装していない。
マニフェストに書いても iOS では効かない。これは回避できる種類の制約ではない。

代わりに、**共有シートに出せるのはショートカット**なので、そこを経由する。

    写真アプリ → 共有 → ［ショートカット］
      1. クリップボードにコピー（入力: ショートカットの入力）
      2. URL を開く: …/shot-bank/?paste=1
    → アプリに出る「クリップボードから取り込む」を押す

ショートカット単体では、画像をアプリの保存領域へ入れることまではできない。
できるのは「クリップボードに置く」と「URL を開く」まで。だから**最後のひと押しは
アプリ側で受ける**。

**paste イベントでは足りない。** iOS には ⌘V が無く、貼り付けの吹き出しは文字を
入れる場所にしか出ない。`navigator.clipboard.read()` を**押せるボタンから**呼ぶ。
iOS は読むたびに確認を出すので、押した流れの中で呼ばないと弾かれる。

**合図（`?paste=1`）が来たときだけ大きく出す。** ふだんは要らないボタンで画面を
埋めたくない。合図は 1 回きりで、読み込み直したときに残らないよう URL から消す。

**同じ絵が複数の形で入っていることがある**（png と HTML など）。1 つだけ採らないと
同じ絵が二重に入る。クリップボードの絵は名前を持たないので、取り込んだ順が分かる
名前を付け直す。

## 未確定・作りながら決めること

- **表情タグの初期セット**は仮。実際に数十枚振ってみて、足りない／要らないを調整する。
- **アニメ顔検出がどこまで拾えるか**は実スクショで確認が要る。
  ガラス越しの小さい顔・全身ショットの小さい顔・2D立ち絵。取りこぼすなら手で枠を足す動線でしのぐ。
- **後ろ姿やボケた人物を「写っている」に数えるか**は使ってみないと決まらない。
  数えるなら手で枠を足す運用、数えないなら話者と検出できた顔だけ、になる。
- **話者チップの色がどれだけ安定しているか**（衣装や場面で変わらないか）は要検証。
  安定していればキャラ照合の裏取りとして強く使えるし、そうでなければ参考値に留める。
- **OCR の誤読は検索のゆれ吸収では埋まらない。** 実測で「香名江」が「理名江」と読まれ、
  「香名江」で検索しても当たらなかった。字形の近い組（力↔カ、口↔ロ など）は寄せているが、
  この手の誤読はきりがない。**Phase 2 の名簿への編集距離照合が本命の解**になる。
- **ヘッダの丸アイコンがどういう条件で出るか**はサンプルが1枚しかない。
  キャラ専用ストーリーのときだけ、という想定で組むが、複数人が主役のストーリーで
  どうなるかは実物を見るまで分からない。**出なくても困らない作り**にしておく。
- **「顔1つ＝話者」の提案がどれくらい当たるか**。切り返しのカットの比率次第。
  外れが多いなら提案自体をやめて、手タグに寄せる。
- **CLIP と軽量モデルのどちらを既定にするか**は、iPhone 実機での実測時間を見て決める。
- ~~**横ストーリーの字幕 OCR** がどこまで実用になるか~~
  → **Phase 1 で確認: 実用にならなかった。** 縁取りを手がかりに字の中身を採る前処理まで
  作ったが、絵の明るい部分も一緒に拾ってしまう。いまは読めなかったものを捨てて空にしてある。
  **横は手入力**に倒すか、字幕の行だけを先に見つける処理を足すかは今後の判断。
