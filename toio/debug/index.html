このブラウザは Web Bluetooth に対応していません。

キャラクタリスティック取得と購読の結果、受信件数

通知は 2 通りの受け方を同時に仕掛けてあります。addEventListener だけに来るのか、 oncharacteristicvaluechanged だけに来るのかで、ブラウザの実装差が分かります。

名前取得notify

受信		onchar
受信		最後の受信

BLEプロトコルバージョン: —

通知が届くかを確かめるマット無しでもできる順に

  1. ボタン — キューブ上面のボタンを押して離す。button の受信が増えれば、 このブラウザで通知そのものは届いている。
  2. ダブルタップ / 衝突 — キューブを 2 回叩く、または軽くぶつける。 sensor の受信が増える。
  3. モーターの応答 — 下の「目標指定を送る」で motor の受信が増える。 応答理由が判定の要。0（正常終了）ならキューブはマットを読めている。 2（toio ID missed）なら読めていない。
  4. 位置ID — マットに載せて手で滑らせる。id の受信が増えれば読めている。

目標指定の応答: —

位置IDの通知テスト設定を変えながら実際に走らせる

止まったままだと「変化があったときのみ」の設定では何も来ません。 そこで設定を書くたびに、前進 0.7 秒 → 後退 0.7 秒で必ず座標を変えて、 そのあいだに位置IDの通知が何件届くかを数えます。

キューブが走ります。マットの真ん中に置いて、前後に 10cm ほどの余裕を空けてから押してください。 全部で 15 秒ほどかかります。

読み出しを有効にすると、ブラウザによっては read の結果が通知としても飛んでくるため、 通知の件数が水増しされます。まずはオフのまま試してください。 



    
通知を入れたまま目標指定で走らせる

    

      ここまでのテストは基本制御（0x01）で走らせていました。目標指定（0x03）で走っている間は、
      キューブが位置IDを読んでいることが応答理由 0 で確実に分かります。
      その最中に位置IDの通知が何を返すかは、まだ一度も見ていません。
      通知を有効にしてから目標指定を送り、到達するまでの受信を数えます。
