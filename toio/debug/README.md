# 🔬 toio BLE デバッグ (`/toio/debug/`)

「位置IDの通知が来ない」の原因を、余計な層を挟まずに確かめるための検査ページ。
**わざと `../shared/toio.js` を使わず、Web Bluetooth を直に叩いている**（ラッパー側のバグの
可能性を除くためと、購読の仕掛け方を実験したいため）。

## 公式ライブラリ（`@toio/cube`）での絶対位置の取り方

npm の `@toio/cube` 1.1.0 のソースを読むと、位置IDの取得は次のようになっている。

1. `peripheral.connect()` → `discoverAllServicesAndCharacteristics()`
2. UUID で振り分け、`10b20101-5b3b-4571-9508-cf3efcd7bbae` を `IdCharacteristic` に渡す
3. `IdCharacteristic` のコンストラクタで、
   ```js
   if (this.characteristic.properties.includes('notify')) {
     this.characteristic.on('data', this.onData.bind(this))
     this.characteristic.subscribe()
   }
   ```
4. 届いたバイト列の先頭で分岐（`id-spec.js`）
   - `0x01` … 位置ID。`x=UInt16LE(1)`, `y=UInt16LE(3)`, `angle=UInt16LE(5)`,
     `sensorX=UInt16LE(7)`, `sensorY=UInt16LE(9)`
   - `0x02` … 標準ID
   - `0x03` … 位置ID missed
   - `0x04` … 標準ID missed
5. `getBLEProtocolVersion()` を待ってから、バージョンに応じて磁気センサーなどを初期化する
   （`initCharacteristics`）。**位置IDはこの初期化の対象ではない**

つまり **位置IDは「購読するだけ」で流れてくる**。読み取りセンサーに対して
設定コマンドを書く必要も、読み出し（read）をする必要もない。
`@toio/cube` はこのキャラクタリスティックを **一度も read していない**ので、
read が `0x00` を返すことは「読めていない」証拠にはならない。

`p5toio`（別実装）も同じで、`CubeIDChar.prepare()` は
`startNotifications()` のあとに一度だけ `readIdInfo()` を呼ぶだけ。
**どちらのライブラリも `0x18`（読み取りセンサーのID通知設定）を書かない。**

### 0x18 は書かないほうがいい

`0x18` で書いた設定は **電源を切るまでキューブに残る**。つまり一度書くと、
そのあとに別のページで繋ぎ直しても効いたままになる。

`../control/` は接続のたびに `18 00 00 ff`（**通知間隔 0**）を送っていた。
「0 が既定」という思い込みで書いたもので、裏は取っていなかった。
間隔 0 が「通知しない」を意味するなら、**接続のたびに位置ID通知を切っていた**ことになる。
この書き込みは外した。素の状態に戻すにはキューブの電源を入れ直す。

このページと `../control/` の実装は、上のシーケンスと同じことをしている。
違いは購読の判定だけで、こちらは `properties.notify` を**見ずに必ず試す**
（このフラグを正しく申告しないブラウザがあるため）。

## このページでできること

### キャラクタリスティックの表

8 つすべてについて、取得できたか・`notify` フラグ・購読できたか・受信件数・最後の生バイト列を出す。

受信件数は **2 通りに分けて数える**。

- `listener` … `addEventListener('characteristicvaluechanged', …)` に来た数
- `onchar` … `oncharacteristicvaluechanged = …` に来た数

両方を同時に仕掛けてあるので、**片方にしか来ない実装**（独自ブラウザにありうる）を見つけられる。

### 通知が届くかを確かめる順番

マットが要らないものから順に試すと、どこで止まっているかが分かる。

1. **ボタン** — キューブのボタンを押して離す。`button` が増えれば、このブラウザで通知は届いている
2. **ダブルタップ / 衝突** — キューブを 2 回叩く。`sensor` が増える
3. **モーターの応答** — 「目標指定を送る」で `motor` が増える。**応答理由が判定の要**
   - `0`（正常終了）… 目標に着いた＝**キューブはマットを読めている**
   - `2`（toio ID missed）… 読めていない
4. **位置ID** — マットに載せて手で滑らせる。`id` が増えれば読めている

1〜3 が増えるのに 4 だけ増えないなら、通知の経路は生きていてキューブが位置IDを
出していないことになる。1 から増えないなら、ブラウザが通知を配っていない。

### 走らせながらの通知テスト

止まったままだと「変化があったときのみ」の設定では何も来ない。そこで **設定を書くたびに
前進 0.7 秒 → 後退 0.7 秒**で必ず座標を変え、そのあいだに位置IDが何件届くかを数える。
間隔 0 / 100ms × 条件 0x00 / 0x01 / 0xFF の組み合わせを順に試す。

始める前に、**いまマットの上にいるか**を目標指定の応答で確かめる（理由 0 なら読めている）。
載っていない状態で「0 件」を集めても意味がないため。

走っているあいだの読み出し（read）も試せる（**既定はオフ**）。止まっているときの読み出しは
`0x00` しか返らなかったが、読み取り中なら値が入る可能性があるため。入るなら、通知が
来なくても定期的な読み出しで位置IDを追えることになる。

ただし **ブラウザによっては read の結果が `characteristicvaluechanged` としても飛んでくる**。
実機のログで確定した。「全部を読み出してみる」を押すと、すべての characteristic で

```
13:06:12.930 rx id(listener) 00 (1バイト)
13:06:12.931 rx id(onchar)   00 (1バイト)
13:06:12.932 rx id(read)     00
```

という 3 連が出る。**以前「200ms ごとに 1 バイトの `00` が通知されている」と見えていたものは、
すべてこの反射だった。**読み出しを止めると通知は 1 件も来ない。
そのため読み出しは既定でオフにし、件数は **中身が仕様どおり（先頭が 0x01 か 0x02）のものだけ**
「うち位置ID」として別に数えている。件数だけ見て成功と判断しないこと。

「目標指定が理由 0 で返るのに位置IDの通知は来ない」という状態のとき、
通知設定と走行の**組み合わせ**を試していないのが穴になりやすいので、それを塞ぐためのもの。

### 通知ONで目標指定を走らせる

上のテストは**基本制御（0x01）**で走らせている。だが「キューブがマットを読めている」ことを
確実に言えるのは**目標指定（0x03）が理由 0 で返ったとき**だけで、
**その最中に位置IDの通知が何を返すかは一度も見ていなかった**。ここが最後に残った穴。

手順は、`0x18`（間隔 0 / 条件 0xFF）を書く → 300ms 待つ → `id` に一時的な傍受を仕掛ける →
目標指定（タイムアウト 10 秒 / 最大速度 80）を送る → 応答が返るまでの受信を数える、というもの。
中身は先頭 8 件までバイト数つきでそのまま出す。

結論の出し方は次の 3 通り。

- 応答理由 0 かつ位置ID 0 件 … **読めていたのに中身は返っていない**。
  この個体・この経路では位置IDをそのまま取れないと考えるのが妥当
- 位置ID 1 件以上 … 取れた
- 応答理由が 0 以外 … マットの上に居なかったので試し直し

### そのほか

- **ID通知設定を書く** — `0x18` を任意の間隔・条件で送る
- **全部を読み出してみる** — 各キャラクタリスティックに read をかけ、結果か失敗理由をログに出す
- **生ログ** — 送受信を時刻つきで残す。位置IDは件数が多いので記録のオンオフを分けてある。
  「全部コピー」でクリップボードに入る（使えない環境では選択用の欄が出る）

## 実装メモ

- ライブラリ非依存。このページだけで完結している
- **接続が終わるまで操作ボタンを塞ぐ。** iOS では characteristic の取得が 1 つ 360ms ほどかかり、
  接続完了まで 3 秒近い。その途中でも `state.*.char` は埋まっていくので、char の有無だけで
  操作を許すと「購読が終わる前にコマンドを送る」ことが起きる。実際に起きて、
  目標指定の応答すら受け取れないログを 1 回無駄にした
- **GATT 操作は 1 本のキューに直列化し、失敗したら 60ms・120ms 待って計 3 回まで
  やり直す。** Android Chrome で `GATT operation failed for unknown reason` が頻発し、
  走行コマンドが 15 件中 10 件（前進は 5 件すべて）落ちていた。キューブが動いて
  いないのに「走らせながら」の結果を集めてしまい、テストが無意味になっていた
- 位置IDの通知はバイト数も出す。1 バイトの `00` が来ているのか、13 バイトの
  位置IDが来ているのかを取り違えないため
- 走らせながらの通知テストは速度 20 で前後 0.7 秒ずつ。元の位置に戻る往復にしてあるので、
  マットの真ん中に置いてあれば端に寄っていかない
- 表は 1 秒ごとに描き直す。受信のたびに描くと、通知が多いときに重くなるため
- 目標指定は制御識別値 0 / タイムアウト 5 秒 / 最大速度 80 / 速度一定で固定。
  切り分けが目的なので、変数を増やさない
