# Starlit Sea 🏮

指でなぞると光の魚が渦を巻く、夜の海のインタラクティブ。
**押さえて溜める → 離すとひらく**、この「間」だけで出来ている。

スマホ全画面前提。ホーム画面に追加するとスタンドアロンで開く（PWA）。

## 操作

| 操作 | 起きること |
| --- | --- |
| タップ | 波紋がひろがり、鈴が鳴る |
| 長押し | 渦がそだつ。画面が沈み、音が上がっていく |
| 離す | **ひらく**。魚が一斉に散り、鳥居が灯り、灯色が満ちる |
| なぞる | 渦がついてくる。魚が尾を引いて流れる |
| 2本指 | 双子の渦。ふたつの渦のあいだで魚がねじれる |
| ダブルタップ | 星が降る（約10秒） |

灯（＝ひらいた回数）が 5 の倍数になっても、勝手に星が降る。
星は一度に湧かせず 10 秒かけて降らせ続ける（一気に出すと 1.5 秒で終わってしまい、
「降っている」時間にならない）。

## 演目

手を止めて眺めていると、ときどきひとりでに動きが起きる。触れば即座に止まる。

| | もとにしたカット | 動き |
| --- | --- | --- |
| **吸い込み** | 5s → 7s → 8s | 集まって、暗くなって、ひらく |
| **天がひらく** | 8s / 13s / 23s | 空の一点から輪が広がる |
| **昇り螺旋** | 22s | 垂直な軸のまわりを回りながら昇り、細くなって先端で弾ける |
| **潮** | 31〜34s | 群れが一様にほどけて、みんなで同じ方向へ流れる |
| **星降り** | 19s / 26s / 40s | 10 秒かけて降り続ける |
| **凪** | 36〜38s | 動きが 1/8 まで落ちる（静かな星降りを重ねる） |

型は目分量ではなく、MV のフレーム間の動きを測って出している。
8fps・192x108 に落とした映像で 16px ブロックのブロックマッチングをかけ、
得られたフローに `u = a + b·x + c·y` のアフィンを当てはめて
**平行移動・発散・回転**に分解した（数値は 1 フレームあたりの画素）。

```
 秒     横     縦    発散    回転   動き量
 2s  -1.65  -0.57  -2.43  24.80   7.67   渦
 5s   0.74   0.05 -16.74   4.48   7.46   集まる
 7s   0.07  -1.64  -2.04   0.00   8.05   昇る
 8s   0.15   0.79  13.77  -5.85  10.83   広がる
13s   1.81  -0.83  13.92   3.41  11.39   広がる
22s   2.40  -2.14   2.28   7.83   4.33   昇る + 回る = 螺旋
32s  -3.05  -0.08  -0.36   1.71   4.13   横へ
37s   0.18  -0.19  -2.18  -2.02   1.11   凪
```

5s の「集まる」→ 7s の「昇る」→ 8s の「広がる」という並びが、MV の
「暗転してからひらく」そのもの。これを 1 本の演目（吸い込み）にしてある。

ひらく直前の「ため」は、**止めるのではなく締める**。減衰と速度上限と流れ場を
まとめて殺すと、暗転と重なって「弾ける前に固まった」ように見えた。いまは
引きを強めながら回りを速くして、輪が締まっていく形で溜める。

### 昇り螺旋は「回る円盤の平行移動」ではない

1 点のまわりを画面全体で回して、その点を上へ動かすのでは螺旋にならない。
それは回る円盤が平行移動しているだけで、魚 1 匹ずつの軌跡は円のままになる。
垂直な軸のまわりの円運動と、軸方向の上昇を組み合わせて初めて軌跡が螺旋になる。

**このアプリのカメラは水面が見えている＝斜め上から見ている。** だから垂直軸
まわりの円は、画面では縦につぶれた楕円に投影される（縦/横 = 0.30）。
正円にすると、真上から見た渦になってしまって画面と合わない。

もうひとつ、螺旋の本質は**高さと位相が結びついている**こと。位相をばらばらに
したまま高さだけ散らすと、巻きが重なって渦の靄になる。高さ h の魚は
`h / ピッチ` だけ位相が進んでいる、という関係を入れて初めてコイルに見える。

### 螺旋が壊れた 2 つの原因

**(1) 位相を「いまの高さ」から引いていた。** 高さが偏るとコイルの一部にしか
魚が居らず、螺旋が途切れる／片側にかたまって軸がずれて見える。いまは逆にして、
曲線を先に決め、そこへ魚を番号順（低不一致列）に一様に配っている。魚がどこに
居ても螺旋はいつでも端から端まで描かれる。

**(2) 高さごとに角速度を変えて位相を積んでいた。** 裾と頂点の角速度差が毎秒
ねじれとして積み上がり、13 秒の終わりには 6 周を超えて模様が潰れる。総ひねりは
1.4 周で頭打ちにして、そのぶん**全体の回りを時間とともに速く**した（渦が
締まると速くなる、という向きは保てる）。

### 昇り螺旋は 2 段構え

いきなり螺旋の場を掛けると、魚は上下にばらけたまま巻きに入る。そこで、

1. **集まる（4 秒）** — 全員を水際（画面下 1/4）の帯へ一様に降ろす。乱数で配ると
   粗密ができるので、黄金比・可塑数の小数部でできる低不一致列で並べる。
   寄る速さは縦横で別々に頭打ちにする。ひとつの上限にすると横の分で使い切って
   縦が伸びず、いつまでも降りてこない。
2. **昇る（9 秒）** — 水際に平たく広い渦ができ、それが上へ伸びながら細くなる。
   頂点で弾け、必ず星が降る。

厳密な曲線に乗せると 1 本の細い帯に潰れて白飛びする。かといって乗せる魚を
減らすと巻きの形が読めなくなる。全部乗せたうえで、線ではなく太さのある管の
まわりに散らすのがちょうどよかった。手前（sin が正）の魚を 1.4 倍まで
大きく描いて、奥行きを出している。

形は円筒ではなく**円錐**にしてある。絞りはほぼ一次（少しだけ裾側を張らせた
二次）。指数を上げて上端でだけ細らせると、見えている範囲では幅が一定に見える。

**裾は「画面をわずかにはみ出す」までにする。** 大きくはみ出すと、下から中ほど
までが一様に見切れて画面いっぱいになり、絞りがまったく読めなくなる。同じ理由で、
径のばらつきも渦（0.87〜1.55 倍）より狭い 1.01〜1.29 倍に抑えている。

巻きは裾から頂点まで 3.5 周。実測（明るさの重心が軸をまたぐ回数）で 3〜4 周。

| 高さ | 螺旋の半径（実測） |
| --- | --- |
| 最上 | 116px |
| 上 | 146px |
| 中 | 153px |
| 下 | 170px |
| 裾 | 176px（画面の半幅 195px を超える瞬間もある） |

魚をどこに詰めるかは時間で変える。前半は全長に一様に配って円錐の形を見せ、
後半の 3 秒でほぼ全員を頂点へ吸い上げてから弾けさせる。弾ける直前の明るさは
上から 46 / 28 / 24 / 3 %。早くから先端へ詰めると裾が空になり、円錐ではなく
細い帯になってしまう。

| 高さ | 幅 | 一周 |
| --- | --- | --- |
| 水際 | 452px | 5.6 秒 |
| やや下 | 437px | 3.7 秒 |
| 中央 | 372px | 2.6 秒 |
| 上部 | 214px | 2.0 秒 |
| 最上 | 68px | 1.7 秒 |

裾は**画面幅（390px）より広い**。そのぶん折り返しの余白も 60px から 210px へ
広げないと、画面の外へ出た魚が反対側へワープする。演目が終わったら 2 秒ほど
かけてゆっくり戻す（急に戻すとまとめて飛ぶ）。

径の絞り方は一次ではなく `hRel^2.5`。一次だと下のほうから細り始めてしまう。
指数を上げると、下は広いまま保って上のほうでだけ絞れる。

裾を下げすぎると、いちばん広いところが画面の外（水面より下）に落ちて円錐に
見えない。裾が水際、頂点が画面上端あたりに来るように置いている。

頂点に近いほど昇る速さも 1/5 まで落ちる。先端に魚が溜まっていき、
8 割ほど進んだところでそこが弾け、**必ず星が降る**（10 秒）。

立ち上がりは急がない。強さを一気に上げると、魚が一点へ吸い寄せられるように
見えてしまう。ふだんの泳ぐ速さ（上限 210px/s）のまま、13 秒のうち前半で
少しずつ集める。

- **頂点は下から伸び上がる。** はじめは水際に平たく広い渦ができて、それが上へ
  伸びながら細くなる。いきなり画面いっぱいの円錐を出すと、垂直方向の目標が
  魚自身の高さと同じになるので、実質水平方向にしか誘導されず、真横から一斉に
  吸い寄せられて機械的に見える
- **参加する時刻を個体ごとにずらす。** 全員が同時に寄ると、一瞬で 1 本の帯に
  なる。参加してからも 2 秒ほどかけて効かせる
- **目標そのものの回転速度を引き継がせる。** 足さないと目標へ最短距離で滑り込む
  だけで、曲がって合流してくれない。ただし遠くの魚まで一緒に回すと速さの
  上限に張りついて寄ってこなくなるので、近い魚にだけ、寄せる速さの頭打ちとは
  別枠で足す

名前は初めて出たときだけ画面に出す。毎回出すと、雰囲気を壊すので。
`?show=rasen` のように指定すると、その演目だけを繰り返す（動作確認用）。

起動直後に「ひらく」を勝手に出していたが、あれは離したときの報酬なので、
触ってもいないのに鳴ると誤タップに見える。やめて、代わりに最初の演目を
4〜7 秒で出すようにした。

## つくり

外部アセットも通信もなく、音も絵もすべてページ内で生成している。
ビルド不要の素の HTML / CSS / JS。

### 絵

- **層を2枚に分けている。** 裏の層（オフスクリーン）は毎フレーム背景色で薄く
  塗り重ねるだけなので、魚の軌跡が尾を引いて残る。鳥居・ブルーム・ビネット・
  波紋といったオーバーレイは表の層に毎フレーム描き直す。
  これを1枚でやると、加算合成のオーバーレイが際限なく溜まって画面が白く飽和する。
- 尾の長さは `1 - (1 - fade)^(dt*60)` で dt に換算しており、**フレームレートが
  落ちても尾の長さは変わらない**。
- 魚は1色につきスプライトを1枚だけ焼き、速度ベクトルをそのまま回転行列に使う
  （`atan2` も `cos/sin` も呼ばない）。速いほど進行方向に引き伸ばすので、
  そのまま流れの筋になる。
- 加算合成なので、群れの数が増えるほど1匹あたりの `globalAlpha` を下げる。
  これをしないと重なったところが白く潰れて色が消える。
- 水鏡は、水面より上の帯を16本に切って上下反転で描き戻している。帯ごとに
  横へずらして波打たせ、ずらした幅ぶん横に食い込ませて継ぎ目を消す。

### 動き

- 流れ場は粗いグリッド（48px）に毎フレーム角度を焼き、魚はセルを引くだけ。
- 全員が同じ流れ場に従うと一本の帯に潰れるので、1匹ずつ違う定常加速を持たせて散らす。
- 渦は**力ではなく速度場**で作る。指のまわりに「回転＋内向きの落ち込み」の
  速度場を定義し、魚の速度をそこへブレンドする。力を足し合わせる作りだと
  輪の半径が `k(r-core) = v²/r` の釣り合い（＝速度上限）で決まってしまい、
  狙った所に来ない。位置で直接ねじ伏せると、今度は半径方向へまっすぐ滑って
  渦に見えなくなる。速度場なら半径も回り方も直に指定できる。
- 接線速度は**芯の内側では剛体回転**（角速度が一定）。並んだ魚の角度の間隔が
  保たれるので、指を動かして輪が崩れても一点に固まらず輪に戻る。外側は
  `(target/r)^0.4` で緩やかに落とす。`1/r` で落とすと遠くがほとんど回らず、
  渦に吸い込まれずまっすぐ滑り込むように見える。
- 半径方向は「目標半径へ落ち込む速さ」を直接指定する。1フレームのあいだ
  接線方向へ直進するぶん、円運動は毎回 `(vt·dt)²/2r` だけ外へずれるので、
  その分をあらかじめ引いておく。フレームレートが落ちても輪が膨らまない。
- 目標半径は溜めリングの 0.56 倍。個体の大きさをそのまま「どの高さを回るか」
  （0.87〜1.55 倍）に使うので、輪はリングの内側に厚みを持って収まる。
  全員が同じ半径だと輪が1本の線に潰れ、加算合成で白く飛んで色が消える。
- 画面下ほど弱く浮き上がる勾配をかけている。水面で押し返す段差にすると、
  魚が水際に一列に貼りついてしまう。

### ひらくときに穴をあけない

距離だけで飛び散る速さを決めると、中心の魚がいちばん速く飛び出してまん中に
穴があく。花火に穴が無いのは「同じ場所から色々な速さで飛び散る」ため。
個体ごとに速さをばらし、遅いものを多めにする（`q * q`）。遅い個体がまん中に
残るので穴があかない。向きも ±0.25rad ほどばらす（きれいな放射は機械的に見える）。

指で溜めてから離したときも、演目の先端で弾けるときも、同じ経路を通る。

### 景色もひとりでに変わる

150〜260 秒に一度、演目の合間に景色が変わる。ひとりでに変わるときは光らせない。
軌跡の層に前の色が残っているので、それだけで勝手に混ざって切り替わる。

### 音

原曲（月見ヤチヨ「星降る海」）の音を実際に測って合わせている。
動画から音声を取り出して FFT にかけた結果:

| | 原曲 |
| --- | --- |
| 調 | **F メジャー**（Krumhansl のプロファイル照合で r=0.88） |
| 旋律帯で多い音 | F4 / C6 / A4 / C4 / C5 / F5 |
| テンポ | 99.4 BPM（1小節 2.41 秒） |
| 0〜400Hz のエネルギー | **62%** |
| 3.5kHz 以上 | **4%** |
| 立ち上がり（10→90%） | 中央値 **190ms** |

つまり「低くて、高域がなくて、立ち上がりが遅い」音。これに寄せる。

- 音階は **F メジャーペンタトニック（F G A C D）を F3〜F5** に取る。
  重なっても濁らず、原曲と同じ調に収まる。いちばん高い倍音でも 1.6kHz。
- 鈴は **整数倍音だけ**（1 / 2 / 3 倍 + 6セントずらした同度）。
  非整数倍音を混ぜると金属的に鳴って尖る。
- 立ち上がりは **48ms** の直線ランプ。減衰しながらローパスが下がっていき、
  時間とともに丸くなる。
- 出口に **ローパス 3kHz + 1.8kHz 以上を −5dB のハイシェルフ**。
  ここを1つ通すだけで全体の尖りが揃って取れる。
- コンプレッサのアタックは 30ms。速いアタックで潰すと、せっかくの緩い
  立ち上がりが締まって尖って聞こえる。
- ひらくと **F3 C4 F4 A4 C5**（F の和音）を 55ms ずつずらして下から積み、
  サブベースが F2 へ着地する。開く音のノイズは 260→880Hz のバンドパス
  （原曲でいちばん厚い帯）で、以前の 7kHz まで上がるハイパスをやめた。

実際にシップされるコードが鳴らす音は、`AudioContext` を計装して確かめている
（発振器の周波数、ゲインのランプ時間、フィルタのカットオフ）。

### 性能

実測フレーム時間から群れの数を自動で増減する（`?q=1` で固定できる。動作確認用）。
1匹あたり `setTransform` + `drawImage` の2コールなので、
スマホで 1000〜1500 匹あたりが目安。

## 出典

月見ヤチヨ「星降る海」の MV に出てくる、暗い間のあとに光がひらく感じと、
寒色から灯色へ転ぶ色の運びに触発された、非公式のファンメイド作品。
楽曲・映像とは関係がない。

## UI

### 無音・スリープ無効

どちらも HUD の歯車の横に置いた。設定パネルの中だけに置くと、いちばん急いで
押したいもの（音を止めたい）が 2 タップ先になる。パネル側にも同じトグルを
残してあり、どちらから触っても両方の見た目が変わる。

入/切は色だけでなく**絵柄も変える**（スピーカー↔×つきスピーカー、目↔月）。
暗い背景では色の差だけだとどちらの状態か読めない。

Screen Wake Lock には 2 つ落とし穴がある。

- **画面が隠れると端末が勝手に解放する。** 戻ってきたときに取り直さないと、
  入れたつもりのまま効かなくなる。`visibilitychange` で取り直している。
- **対応していない端末がある。** 黙って効かないのがいちばん困るので、
  そのときは入にせず理由を出す。要求が拒否されたときも同じ。

### シートのハンドル

タップでの開閉に加えて、掴んで動かせる。離したときの行き先は

1. 速度が 0.35px/ms を超えていれば、その向きへ
2. そうでなければ、travel の 3 割を越えたかどうかで決める

速度は**直近 140ms の幅**で測る。直前の 1 点との差だと、指を離すのは最後の
move の直後なので経過時間がほぼ 0 になり、ゆっくり動かしただけでも巨大な
速度が出て逆へ弾かれる（実際そうなった）。

行き先のしきい値を真ん中（travel の 5 割）にすると、開いた板を閉じるのに
画面の半分ぶん引く必要があって重い。どちら向きでも 3 割で乗り換える。

### 月

元になった映像では月に見えているが、実際はミラーボールなので兎も海もない。
だから**ただの白い丸**にしてある。

明るさはかなり控えめ。加算で乗せて、宵の空（6,10,22）の上で中心が
(103,107,119) くらい。魚より暗いので前へ出てこず、空が空いたときにだけ
「そこに在る」ように見える。強くすると、空に丸を貼ったように浮く。

円のふちから外へ長く薄い暈を伸ばしている（円の半径の 7 倍まで）。これが無いと
切り抜きに見える。ふちも 1px ぶんだけぼかす。

位置は画面の中央から右へずらす。螺旋も鳥居も画面の中央にあるので、真上に
置くと重なる。横向きのときに HUD の下へ潜らないよう、上端からの余白は
最低 76px 取る。鳥居より先に描くので、重なったときは鳥居が手前になる。

## 裏へ回って戻ると重くなっていた

`frame()` の中で `requestAnimationFrame` を呼びっぱなしにして、止めるのは
「フラグを見て return する」だけだった。ところが裏へ回った時点で予約済みの
コールバックが 1 個宙に浮いたまま残り（裏では発火しない）、戻ってきたときに
新しく 1 個予約するので、往復するたびに 1 本ずつループが増える。

実測（1 フレームあたりに走ったループの本数）:

| 裏↔表の往復 | 直す前 | 直したあと |
| --- | --- | --- |
| 0 | 1.0 | 1.0 |
| 1 | 2.0 | 1.0 |
| 2 | 3.0 | 1.0 |
| 3 | 4.0 | 1.0 |
| 4 | 5.0 | 1.0 |

予約 ID を控えておいて、止めるときは `cancelAnimationFrame` で取り消す。
起こすときは「すでに回っていたら何もしない」を通す。

測り方の注意。**「1 秒あたりのコールバック数」で測ると気づけない。**
表示のフレームレートはコンポジタ側で決まるので、ループが何本あっても
1 秒あたりのフレーム数は変わらない。増えるのは 1 フレームあたりの本数のほう。
最初この指標で測って「直す前でも増えていない」と誤診した。

また、裏へ回す再現も素直にはできない。`document.hidden` を差し替えて
`visibilitychange` を投げるだけでは rAF が実際には止まらないので、
宙に浮いたコールバックがその場で消化されて再現しない（ヘッドレスでは
タブを前面に出しても `hidden` が false のまま）。rAF を包んで「凍っている
あいだは配らずに溜める・戻したら溜めたぶんを配る」を作って、初めて再現した。

## 星降り

### 角度

以前は x 軸からの角度で持ったうえ、横方向にだけ 0.55 を掛けていた。そのせいで
画面上の実際の傾きが真下から 5〜19 度にしかならず、ほとんど真下に落ちていた。
いまは「真下から何度傾いているか」をそのまま持つ（30〜40 度）。

向きは 1 回の星降りのあいだ揃える。バラバラだと交差して、ただの散らかった線に
見える。斜めに流れるぶん、湧かせる範囲は風上側へずらす。

実測（描かれた線の主軸。太い塊＝魚を開処理で取り除いてから測った）:
10 本で中央値 36.7 度、範囲 31.8〜41.5 度。

### 着水

水面に届いた星は、そこで消えて波紋ひとつと 4〜7 個のしぶきを残す。しぶきは
入ってきた勢いのぶんだけ前へ流れ、重力 900 で落ちてくる。軌跡の層に描くので
短い尾を引く。波紋は水鏡より前に描いているので、水面に映り込む。

このとき、寿命も直した。0.9〜1.9 秒だったが水面までは 1.0〜2.2 秒かかるので、
届く前に消えるものが多く着水がまばらだった。ふつうは寿命ではなく着水で消える。

波紋は指の波紋と同じ配列を使うが、大きさと寿命は別に持たせている。`addRipple`
の power をいくら小さくしても、輪が画面規模まで広がってしまうため。

## 景色は切り替えではなく混ぜる

`S.scene` を「いま画面に出ている景色」を入れる可変オブジェクトにして、
切り替えのあいだは 2 つの定義の中間値を入れる。読む側（描画・魚・鳥居）は
今までどおり `S.scene` を見るだけでよい。1.5 秒かけて混ぜる。

名前と印だけは押した瞬間に変える。1.5 秒待たされると、押しても反応が無いように
見えるため。

焼き直し（魚のスプライト・鳥居・水面のグラデーション）は毎フレームやると重い。
スプライトと水面は 0.1 秒ごと、鳥居は 0.3 秒ごとに間引く。軌跡の層が前の色を
持っているので、多少とびとびでも段には見えない。

## 螺旋は「詰める」のではなく「登らせる」

終盤に形が崩れていた。原因は、分布を頂点へ寄せて溜めていたこと。裾が空になり、
円錐が細い帯に潰れて、螺旋そのものが読めなくなっていた。

いまは軸も裾も動かさず、魚の居場所だけを曲線に沿って進める（`SH.hflow`）。
一周ぶん登った魚は裾へ戻すが、**泳がせて戻すのではなく位置ごと移す**。
泳がせると、螺旋を逆走する筋がずっと見えてしまう。移すときに大きさを 0.12 まで
絞るので、水際で湧いたように見える。

弾ける手前だけ流れを 4 倍に上げて、駆け上がる感じを出している。

螺旋のあいだの減光（加算で白飛びしないように魚を暗くし尾を短くする）は、
以前は `SH.hr > 1` の真偽で切り替えていた。螺旋が始まった瞬間に画面がガクッと
暗くなるので、始まって 1 秒おいてから 1 秒かけて落とす。

## 設定パネルがスクロールできない

`vh` を使っていたのが原因。**iOS Safari の `vh` は「ツールバーが隠れていると
きの高さ」**なので、ツールバーが出ていると `max-height: 86vh` の板の下端が
画面の外へ出る。中身は `max-height` の中に収まっているからスクロールも起きず、
下の行に手が届かない。`dvh`（いま見えている高さ）に変えた。`vh` の宣言を
残してあるので、非対応の端末はこれまでどおりになる。About（余地 463px）も同じ。

Chromium では再現しない（`vh` と `dvh` が同じ値になるので）。手元で試した
範囲では次のことも分かっている。

- **「1 秒あたりのコールバック数」型の誤診を避けるため、まずハーネスを検算する。**
  CDP の `Input.synthesizeScrollGesture` は、この環境では素の div すら
  スクロールさせられなかった。これで測ると「どこも動かない」と出てしまい、
  実際そう誤診した。`Input.dispatchTouchEvent` で touchStart/Move/End を
  自分で流す形にしたら、素の div が 0 → 165 と動いた。
- **`html, body { touch-action: none }` は今回の原因ではなかった。** body に
  none を置いた素の div でも指で 162px スクロールした。それでも外したのは、
  ここに置く必要がそもそも無いから。ページを動かさないのは `overflow: hidden`
  と `overscroll-behavior` の仕事で、`none` はキャンバスにだけ要る。

## 螺旋が終盤に「中央へ収束した直線」になっていた本当の理由

分布を頂点へ寄せるのをやめても、まだ潰れていた。原因は**角速度の予算超過**。

螺旋に沿って登ると、**登るだけで角度が `総ひねり × 登る速さ` ぶん動く**。
3.5 周の螺旋を毎秒 0.075 周ぶん登れば、それだけで 1.65 rad/s になる。
全体の回り 0.89 rad/s と足して 2.5 rad/s。裾（半径 237px）では目標が
**600px/s** で動くことになるが、魚の上限は 432px/s、目標へ寄る速さの頭打ちは
265px/s。つまり外周の魚は原理的に追いつけない。

そして遅れた魚は `near` ゲート（280px）から外れて公転成分を失い、円の内側を
最短距離で突っ切る。これが「中央へ収束してまっすぐな帯になる」の正体だった。
終わりぎわに流れを 2.2 倍していたので、そこで 4.5 rad/s・1068px/s まで跳ね、
いちばん崩れて見えていた。

直し方は、**裾の接線速度に予算を置いて、全体の回りと登りで分け合う**こと。

| | |
| --- | --- |
| 裾に出させる接線速度 | 320px/s |
| 使える角速度 | 1.35 rad/s |
| うち全体の回り | 0.30 rad/s |
| うち登り | 1.05 rad/s（= 0.048 周/秒） |
| 14.7 秒で登る量 | 0.70 周ぶん |

`near` ゲートも 0 に落とさず下限 0.34 を持たせた。0 にすると、いちど遅れた魚が
公転をやめて内側を突っ切り、そのまま戻れなくなる。

実測（水面より上で光っている画素の広がり、演目の後半）:

| 経過 | 直す前 | 直したあと |
| --- | --- | --- |
| 中盤 | 219px | 226px |
| | 178px | 270px |
| | 184px | 242px |
| | 184px | 248px |
| 弾ける直前 | **88px** | **260px** |

弾ける直前の高さ帯ごとの半径も、上 66 / 108 / 162 / 裾 167px と円錐のまま。

## 「演目を出す」が消えていた

`.sheet-body` は縦の flex。**中身がはみ出すと、既定で子が縮む**（`flex-shrink: 1`）。
文字を持つ行はある程度で止まるが、`details` は `overflow: hidden` と相まって
高さ数 px まで潰れ、丸ごと消えたように見えていた。実測で画面 750px のとき 7px、
667px のとき 2px（本来 42px）。

`dvh` に直してパネルが「見えている高さ」基準になったぶん中身がはみ出しやすく
なったので、そこで表面化した。`.sheet-body > * { flex: 0 0 auto }` で行を
縮ませないようにして直した。

なお、この環境（サンドボックス）から GitHub Pages の URL は引けない。
`curl` は 0 バイトを返すので、「配信に乗ったか」を curl で待つ仕掛けは
いつまでも成立しない。配信の確認は Actions の run の結果を見ること。

### 頂点で魚が消えて見えていた

一周ぶん登った魚を裾へ「位置ごと移す」ようにしているので、頂点で魚がぱっと
消えるのがそのまま見えていた。曲線の両端（前後 7%）で大きさを 0 まで絞る
envelope をかけて、**細って消え、裾で湧いて育つ**往復にした。位置を移す瞬間は
すでに大きさが 0 なので、入れ替わりが目に触れない。

### 弾ける → 星降り は 1 秒あける

同時に出すと、弾けたのか星が降ったのか分からない一塊になる。`hu` は演目の
長さで伸び縮みするので、1 秒ぶんを `1 / (dur × (1 - GU×0.82))` から毎回
出している（19.5 秒なら 0.068）。実測で、明るさのピークから流星が現れるまで
実時間 1.86 秒（ヘッドレスは実時間の約 0.55 倍で動くので、アプリ内で 1.0 秒）。

## 潮を 16〜20 秒にして、緩急をつける

演目の長さは `show.dur` に持たせて、回ごとに変えられるようにした（潮は毎回
16〜20 秒）。同じ尺で繰り返すと型が読めてしまうため。

一定の強さで流しっぱなしにすると、途中から「ただ動いている」だけになる。
潮なので、寄せては緩めるをゆっくり繰り返す。強さを 0.10〜1.00 で揺らす。

**山の数は長さから決めるが、2〜3 に収める**（`clamp(round(dur / 7.5), 2, 3)`）。
`u` に対して固定の山数にすると、長い回では 1 山 15 秒になって緩急が読めない。
かといって数を増やすと、谷（強さ 0.10）のたびに群れが止まって見える。
止まるのは山と山のあいだの **1〜2 回**までにしたい。

実測（明るい塊の横長さの中央値。横へ速く流れるほど魚は横に伸びて描かれる）:

| | |
| --- | --- |
| 演目なし | 0.77 |
| 1 つめの山 | 2.17 |
| あいだの谷 | 0.72 |
| 2 つめの山 | 2.20 |
| 終わりぎわ | 1.06 |

山ごとに潮騒を重ねている。長くなったぶん、音が頭だけだと途中で切れて聞こえる。

## 潮を「みんなで同じ方向へ」にする

上の版の潮は、横向きの加速度（`SH.lat`）を毎フレーム足しているだけだった。
めいめい勝手に泳いでいる群れに横流れが乗るので、全体としては「なんとなく
片側に寄っている」以上にはならず、演目に見えない。

足すのをやめて、**群れの速度そのものを一本の共通の速度にする**。
向きは毎回ランダムに選び（`show.a0`）、そこから周期のちがう 2 つの正弦で
ゆっくり振る。振れ幅は合わせて ±48 度。1 つだけだと行って戻るだけの往復に
見える。

### 筋をほどいて一様に散らす

ただ同じ方向へ流すだけだと、流れ場が作った**筋**（魚が線状に集まった
かたまり）がそのまま平行移動する。狙いは星空の長時間露光——一様な点が
平行に流れる絵なので、筋はほどきたい。

そこで「一様に散らばった目標の並び」を先に作り、それを流れと一緒に平行移動
させて、魚をそこへ寄せる。

- 並びは乱数ではなく **R2 列**（可塑数の小数部 0.7548776662 / 0.5698402910）。
  乱数だと粗密ができて、ほどいた先がまた筋に見える。
- 並びは升目の **0.38 倍**だけ個体ごとに散らす。R2 列そのままだと規則正しすぎて
  壁紙の模様に見える。散らす量は固定なので、目標の並びは平行移動するだけで
  形は変わらない。
- ずれは**折り返しをまたいだ側**で測る。素直に引くと、画面の端で目標だけ先に
  反対側へ回ったときに、魚が画面を横断して追いかける。
- 目標そのものの速度（＝潮の速度）を足してから寄せる。足さないと、減衰と
  釣り合うところまで遅れてから流れることになる。
- 寄せる速さは 110px/s で頭打ち。強いと、演目の頭で全員が持ち場へ一直線に
  飛んで「整列した」ように見える。
- めいめいの泳ぎ（流れ場と個体の癖）は 0.4 倍まで弱める。0 にはしない。
  0 にすると隊列が硬直して機械に見える。

一様に散らす強さ（`SH.drift`）は寄せ引きの `swell` では緩めない。緩めると、
谷で群れがまた筋にもどってしまう。

立ち上がりは `u` ではなく**秒**で数える（2.2 秒）。`ease` で立ち上げると、
演目が長いほど揃うまでの時間まで一緒に伸びて、「やっと揃ったら終わり」が
いつまでも変わらない。引くほうは `ease` に任せるが、0.55 で割って終わりぎわ
だけに効かせる。

実測（アプリ内の時刻 `show.t` で数えた、4 回ぶん）:

| 長さ | 一様（変動係数 0.36 未満）でいた時間 | 止まった回数 |
| --- | --- | --- |
| 18.4s | 11.1s | 1 |
| 19.0s | 9.4s | 2 |
| 17.9s | 8.5s | 1 |
| 16.9s | 11.2s | 1 |

揃うまでにかかるのは 4.7〜6.8 秒。ここは寄せる速さの頭打ち（110px/s）で
決まるので、演目を伸ばしても縮まない。だから一様でいる時間はほぼ
「長さ − 8 秒」になる。

実測（390×844、粗いマス目 8×16 の明るさの**変動係数**＝小さいほど一様、
構造テンソルの**異方性**＝1 で筋が全部平行）:

| | ばらつき | 向きの揃い |
| --- | --- | --- |
| 演目なし | 0.49〜0.58 | 0.15〜0.27 |
| 潮のさなか | **0.32** | **0.67** |

筋の角度は回ごとにちがい（実測 3 回で 153°／25°／111°）、1 回のあいだにも
ゆっくり動く。

## 凪に静かな星降りを重ねる

凪は動きを 1/8 まで落とす演目だが、それだけだと画面が「凪いだ」ではなく
**「止まった／固まった」**に見える。動いているものを 1 つだけ残したい。

そこで星降りに濃さ `fallK` を足して、凪のあいだは通常の **25%** で降らせる。
星は `SH.calm` の影響を受けないので、魚が止まっているあいだも星だけが降り、
着水して波紋を立てる。

- 演目より **1.2 秒長く**降らせる。魚が動きだすころに、星のほうがなだらかに引く。
- 鳴る間隔も濃さで割る。数だけ減らして音がそのままだと、見えていない星の音が
  鳴っているように聞こえる。
- 濃さのちがう星降りが重なったら濃いほうに合わせる。凪のさなかに指で呼んだのに
  静かなままだと、反応が無いように見える。

実測（同時に画面に出ている流星の数の中央値）:

| | |
| --- | --- |
| 星降り | 15.0 |
| 凪 | 4.0（**27%**） |

## 魚の形

元の映像の魚はふっくらではなく細長い。参照画像の魚 132 匹を連結成分の
**長軸／短軸**で測ると、中央値 3.22（四分位 2.71〜3.81）。

同じ測り方でこのアプリを測ると 2.49（2.18〜2.85）で、明らかに丸かった。
胴を長く細くして寄せた。

| | 細長さ 中央値 | 四分位 |
| --- | --- | --- |
| 参照画像 | 3.22 | 2.71〜3.81 |
| 直す前 | 2.49 | 2.18〜2.85 |
| bw = 0.27（行き過ぎ） | 4.07 | 3.40〜4.98 |
| bw = 0.34 | 3.39 | 2.84〜3.93 |
| **bw = 0.36（採用）** | **3.29** | **2.71〜3.83** |

細長さはほぼ `1.15 / bw` で動くので、目標から逆に幅を決められる。

胴が細くなって面積が減るぶん、濃さを上げて群れの明るさを保った
（実測 平均輝度 41.0 → 41.9）。尾の又は、胴が細くなったぶん相対的に
大きくして、絶対の大きさは元と同じに保っている。

### 湧くのは水の中だけにする

一周した魚は裾で湧く（位置ごと移す）。その湧いてから見えきるまでの帯が
水面より上に出ていると、**何もない空中に魚がふっと現れて**見える。

原因は、裾を演目の進みで `0.94H → 0.84H` と持ち上げていたこと。終盤には湧きの
帯の上端が水面より 80px も上に出ていた。

- 持ち上げるのをやめ、裾は「湧きの帯が丸ごと水に入る高さ」から決める。
  楕円の縦ぶれ（±R·hk）ぶんの余裕も見る。
- 裾では大きさのばらつきによる縦ずれを 0 にする（湧く場所を水面から遠ざける）。
- 位置を移すときも `waterY + 10` より下に押さえる。
- 円錐の半径を高さでも頭打ちにする。横向きだと W だけで決めると円錐が水深より
  広くなり、湧く帯がどうやっても水面から出てしまう。

| 画面 | 裾 | 湧き終わりの最高点 | 水面 | |
| --- | --- | --- | --- | --- |
| 390×844 | 802 | 676 | 641 | 水の中 |
| 390×667 | 634 | 519 | 507 | 水の中 |
| 430×932 | 885 | 747 | 708 | 水の中 |
| 844×390（横） | 388 | 294 | 296 | 2px はみ出し |

### 序盤に鳥居のあたりで湧いて見えていた

湧く位置を水中に押さえても、**序盤だけ**まだ空中に魚が出ていた。原因は 2 つ。

**集める時間が足りていなかった。** 全力で集める窓は u 0.09〜0.24 の 2.9 秒。
いちばん遠い魚は 654px 降りる必要があり、縦の頭打ち 225px/s では最短 2.9 秒。
余裕ゼロなので、間に合わない魚が必ず空中に取り残されていた。窓を 3.7 秒に
伸ばし、頭打ちを 285px/s に上げて、余裕 1.4 秒にした。

**取り残された魚がそのまま光っていた。** 螺旋に参加するまで（`join` は
hu 0.02〜0.20 でばらつく）steering が何も掛からず、空中に散らばったまま
見えていた。円錐が水面より上へ伸びきるまで（hu 0.35 まで）は、水面より上の
魚を伏せる。ただし 0.22 までしか落とさない。消しきると、降りていく群れごと
見えなくなってただ画面が空になる。

実測（水面より上で光っている画素）:

| 経過 | 直す前 | 直したあと |
| --- | --- | --- |
| 1.4s | 25,898 | 6,816 |
| 2.8s | **55,640** | **16,881** |
| 4.1s | 50,151 | 13,073 |
| 5.4s | 30,251 | 4,594 |
| 6.7s | 2,865 | 123 |
| 13s 以降（螺旋） | 21,671 | 20,425 |

螺旋ができてからの明るさは変わっていない。変わるのは序盤だけ。

## 時計

**月の下**に、ロック画面くらいの大きさで置く。秒は分の右隣に小さく控えめに。
既定は切で、無音・スリープ無効と同じく HUD のボタンと設定パネルの両方から
入り切りできる（どちらから触っても両方の見た目が変わる）。

大きさは参照画像から測って決めた。「21:25」の字の高さが画面高の **9.2%**
（画面幅に対する幅は 62%）。目分量で `px` を決めるとフォントによってずれるので、
`measureText` で 1 回測って `px = 100 × 目標の字高 ÷ 測った字高` と割り出す。
実測で 390×844 のとき字の高さ 76.5px（目標 77.6px）。

位置は送り幅ではなく**インクの箱**で決める。送り幅だと、字によって
サイドベアリングのぶんだけ揃わない。時刻はインクの中心を月の真下に、秒は
インクの左端を分の右端＋余白に置き、ベースラインをそろえる。

明るさは月と同じ（実測 最大輝度 時計 107 / 月 101）。秒はその 0.55 倍。

毎フレーム `fillText` すると、にじみ（`shadowBlur`）ぶん高くつく。文字が
変わったときだけ焼き直す（＝秒がくり上がる 1 秒に 1 回）。

アイコンが 4 つになったので、詰める幅を 360px → 400px に広げた。390px
（iPhone の標準的な幅）だと、そのままでは題字が 2 行に折り返す。
320 / 360 / 390 / 414 / 430px のすべてで 1 行に収まることを実測で確認。

## 重かった本当の理由は、水鏡がキャンバスを自分自身から読んでいたこと

スマホが熱くなり、PC でもすこし引っかかる、という話から測った。

まず CPU プロファイルを取ると、**91.3% が `drawImage`**。物理（`step`）は
0.03% で、完全に描画側の問題だった。

| | |
| --- | --- |
| `drawImage` | 91.3% |
| `(program)` | 7.8% |
| `render` 本体 | 0.2% |
| `step`（群れの計算ぜんぶ） | 0.03% |

次にどの `drawImage` かを切り分ける。ここで一度しくじった。`render` の中に
区間タイマーを入れて測ると「波紋 67%・魚 32%」と出るが、これは嘘だった。
Canvas2D は命令を溜めておいて、**読み戻しが要るところでまとめて流す**ので、
時間が「溜まっていたものを流した場所」に付く。区間タイマーではなく、
機能を 1 つずつ切って実測した。

    そのまま      15.9 fps
    水鏡オフ      40.2 fps   （2.52 倍）

犯人は水鏡だった。水面の映り込みは、揺らぎを出すために 16 本の帯に分けて
描いている。その帯を**キャンバス自身から** `drawImage` していた。

```js
ctx.drawImage(cv, 0, sy, WD, bh, off - pad, sy, WD + pad * 2, bh);
//             ^^ cv は、いま描き込んでいるキャンバスそのもの
```

書き込み先から読むので、ブラウザは呼ばれるたびに元の絵を取り直す。16 本ぶん、
1 フレームに 16 回。

**直し方**：映すもとの帯（水面より上）を、いちど別のキャンバスへ写してから
16 本を描く。読み取りは 1 回で済み、**出てくる絵は 1 画素も変わらない**。

    そのまま（直したあと）   40.5 fps   （2.55 倍）
    水鏡オフ                46.0 fps   （差は 14% まで縮んだ）

残るいちばんの山は魚のスプライト（描かないと 33.6 → 60.2 fps）。これは
見た目そのものなので触っていない。

## 群れの数が、いちど減ったら二度と戻らなかった

数は実測 FPS で自動調整している。落とすほうは効いていたが、戻すほうが
**原理的に一度も発火しない**条件だった。

```js
if (ms > 21) { slow++; }            // ms = フレームの間隔
else if (ms < 13.5) { fast++; }     // ← ここ
```

`ms` は rAF の間隔なので vsync で頭打ちになる。60Hz の画面では、どれだけ
余裕があっても 16.7ms から下がらない。つまり 13.5ms は永久に満たされない。

実測（320x480・DPR1、コマ落ちがほぼ無い状態）:

| | |
| --- | --- |
| フレームの間隔 平均 | 16.7ms |
| 1 フレームで実際に使った時間 平均 | 8.8ms |
| コマ落ち（間隔 > 21ms） | 0.2% |
| **旧ルールが「余裕あり」と判定** | **0.0%** |
| 新ルールが「余裕あり」と判定 | 5.8% |

戻すほうは、間隔ではなく「1 フレームで実際に使った時間」が間隔の何割かで
見るようにした（`work < min(9, ms × 0.55)`）。割合で見るので 120Hz の画面にも
そのまま効く。9ms の頭打ちは、間隔が伸びているときに「割合では余裕」に
見えてしまうのを避けるため。落とすほうは間隔のままでよい。21ms を超えている
＝実際にコマを落としているので、原因が CPU でも GPU でもそこに出る。

実測で、`quality` を 0.35 に落とした状態から放っておくと
0.45 → 0.65 → 0.75 → 0.85 → 0.95 と戻るようになった（魚 210 匹 → 570 匹）。

## 景色の切り替えで、空中に魚が湧いていた

景色ごとに群れの密度がちがう（宵 1.0 / 灯 0.92 / 沖 1.18 / 銀 1.4）。切り替えの
1.5 秒のあいだに数を合わせるので、密度が上がる向きだと魚を足すことになる。
その置き場所が画面ぜんぶ（`rnd(0, H)`）だったので、水面より上にも湧いていた。
何も無い空中に魚がふっと現れるのは、そのまま見える。

実測（390x844、宵 → 銀）:

| | 直す前 | 直したあと |
| --- | --- | --- |
| 足した魚 | 470 匹 | 470 匹 |
| うち**空中**に湧いた | **360 匹（77%）** | **0 匹（0%）** |
| 水中に湧いた | 110 匹 | 470 匹 |

77% なのは、水面が画面の 76% の高さにあるから。一様に置けばそうなる。

- あとから足すぶんは水面より下だけに置く。
- 上へ向かせる。水際で横に散ると、水面に沿って並んだ帯に見える。
- 大きさ 0 から出す。1 のままだと、水の中とはいえ「ぱっと現れた」のは見える。
  演目の外では `dep_` が 1 へ戻っていくので、そのまま 0.5 秒ほどで育つ。
- **はじめの 1 回だけは画面ぜんぶに散らす**（`N === 0` で見分ける）。ここまで
  水中に寄せると、開いた瞬間に画面の下だけに魚がかたまっていることになる。

実測で、起動時の配置は今までどおり空中 897 匹 / 水中 279 匹だった。
